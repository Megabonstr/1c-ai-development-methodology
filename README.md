# 1С-разработка: от входящей задачи до проверенного результата

**Практический рабочий процесс для 1С-разработки: от сырого запроса клиента или аналитика до проверенного изменения с понятной историей результата.**

Репозиторий собирает в один последовательный рабочий процесс привычные практики разработки: понять реальную задачу, проверить текущий проект и стандартные механизмы, внести минимально достаточное изменение, доказать результат и сохранить контекст так, чтобы к доработке можно было нормально вернуться позже.

ИИ здесь используется без иллюзий и магии: он не заменяет разработчика и не снимает с него ответственность за решение. Он сокращает время на самые дорогие ручные этапы: разбор переписки, ТЗ и созвонов, поиск по исходникам и метаданным, исследование документации и примеров, сравнение механизмов, рутинную реализацию, проверки и подготовку документации. Само решение по задаче и приёмка по-прежнему опираются на факты проекта и реальные проверки.

Если вы нашли проблему, противоречие или реальный контрпример, создайте Issue по [правилам обратной связи](CONTRIBUTING.md). ## Кому это может быть полезно

**Новичку** - чтобы с первых реальных задач учиться решать их профессионально: сначала понять результат и границы, проверить текущий проект и стандартные механизмы там, где это нужно, затем реализовать, проверить и оставить понятную историю. Не обязательно осваивать эти привычки только после ошибок на рабочей базе.

**Практикующему специалисту** - как структурированная методика в одном месте: разбор входящей задачи, проверка текущего проекта и источников, ограниченная реализация, проверка изменений и результата, долговременная история и работа с ИИ. Её можно сравнить со своим процессом и использовать только те части, которые реально его усиливают.

**Опытному разработчику, архитектору или техлиду** - как база для сравнения и усиления собственного процесса, а также для критики самой методики. Реальные контрпримеры, более сильные механизмы и доказательства важнее сохранения правил ради самих правил.

Если хотите спорить с правилом, предложить улучшение или принести контрпример, сразу смотрите [правила оформления Issues и обратной связи](CONTRIBUTING.md).

**Для всех** - чтобы понимать и сам процесс разработки, и реальные возможности и ограничения ИИ. Если убрать ИИ, основной подход должен продолжать работать.

Если слово **Issue** пока непривычно: это обычная карточка задачи, ошибки, вопроса или предложения в GitHub. В нашей схеме Issue удобно использовать как долговременное место, где остаются цель задачи, важные решения, проверка и итог. Подробнее: [что такое Issue и как он участвует в рабочем процессе](docs/ru/GIT_GITHUB_FLOW.md#issue).

## Выберите, зачем вы здесь

Переходите сразу в [Быстрый старт](docs/ru/GETTING_STARTED.md). Читать весь репозиторий заранее не нужно.

Можно просто дать способному агенту ссылку на этот репозиторий и написать:

> Посмотри, полезна ли эта методика нашему проекту. Сначала изучи текущие инструкции и структуру проекта, ничего не меняй без разрешения. Если подходит - предложи минимальный безопасный способ подключения.

Текущий способ подключения - **закреплённая копия выбранной версии пакета** с сохранением проектных инструкций. Автоматический безопасный установщик с обновлением и удалением пока не поставляется.

### Уже разрабатываю с ИИ и хочу сравнить или усилить свой процесс

Начните с [подключения и источников](docs/ru/SOURCES_AND_ADOPTION.md) и [структуры проекта](docs/ru/PROJECT_STRUCTURE.md).

Сначала сравните существующие инструкции, навыки и процесс проекта с этой методикой. Не заменяйте рабочие правила вслепую: результатом сравнения может быть **ничего не устанавливать**, взять только отдельные идеи или подключить пакет целиком.

### Хочу сообщить об ошибке или предложить улучшение

Перед созданием Issue прочитайте [правила обратной связи и оформления Issues](CONTRIBUTING.md).

Там коротко описано, как оформить ошибку, предложение или критику так, чтобы её можно было проверить и превратить в изменение.

### Хочу изучить методику подробно

Начните с раздела ["От задачи до результата"](#от-задачи-до-результата), затем используйте [гайд для новичка](docs/ru/BEGINNER_GUIDE.md) и навигацию по отдельным темам ниже.

### Пока не планирую использовать ИИ

Методика остаётся применимой: понять задачу, проверить существующие механизмы, внести минимальное изменение, доказать результат и сохранить историю полезно и без агента.

Начните с ["От задачи до результата"](#от-задачи-до-результата). Раздел ["Где ИИ экономит время - и где всё равно нужен контроль разработчика"](#где-ии-экономит-время--и-где-всё-равно-нужен-контроль-разработчика) показывает, что именно ИИ может ускорить.

## От задачи до результата

В реальном проекте задача приходит от клиента, аналитика, руководителя, поддержки, из тикета, переписки, созвона или голосового сообщения. Иногда она точная, иногда - это поток мыслей, бизнес-боль и предположение "как лучше сделать".

Рабочий цикл:

    пришла задача
    → разобраться, какой результат действительно нужен
    → при необходимости разделить её на части
    → коротко зафиксировать границы и способ проверки
    → проверить только существенные неизвестные
    → посмотреть текущий проект / БСП / стандартный механизм / подходящий пример
    → выбрать минимальный подходящий путь и реализовать
    → проверить теми способами, которые реально доказывают результат
    → принять результат
    → сохранить короткий итог: что, где, как проверено и какая версия принята

## Философия

Это не набор обязательных ритуалов и не попытка объявить единственно правильный способ разработки 1С. Правила должны помогать получать хороший, проверяемый результат и упрощать дальнейшее сопровождение. Если правило мешает реальной работе без достаточной причины - его нужно менять.

### 1. Сначала проверенные механизмы, потом своё

Перед существенной доработкой сначала смотрим, как задача уже решается в текущей конфигурации и существующем коде.

Если готового решения нет - проверяем подходящие типовые механизмы 1С, БСП, официальную документацию и доказанные примеры. Собственный механизм пишем для того пробела, который действительно остался.

Это не означает "исследовать всё подряд". Если нужный механизм уже известен и подтверждён - можно сразу работать.

### 2. Контроль и история изменений

Существенная доработка должна оставлять понятный след:

- что попросили;
- что изменили;
- почему выбрали этот путь, если выбор был важен;
- как проверили;
- какая версия была принята;
- что осталось неизвестным или отложенным.

Git и GitHub - основной рекомендуемый способ хранить такую историю, но сам принцип шире конкретного инструмента: важное состояние задачи не должно существовать только в чате или памяти разработчика.

### 3. Экономить контекст и не тащить весь проект в каждую задачу

Агенту не нужно читать всю конфигурацию, всю историю задач, все исследования и все инструкции.

Нормальный путь - передавать только то, что нужно для текущего шага: точную задачу, нужные исходники, существенные ограничения и проверки.

Чем меньше лишнего контекста, тем дешевле работа и тем меньше вероятность, что агент уедет в сторону.

### 4. Доказательства важнее заявлений

Фраза "всё работает" ничего не доказывает сама по себе.

Чтение исходников, статическая проверка, тест, сборка, загрузка в базу, выполнение в 1С, проверка формы и пользовательская приёмка - разные виды подтверждения.

Если нужная проверка не выполнена, это нужно честно отметить, а не заменять уверенностью модели.

### 5. Один основной исполнитель, помощники - только когда они полезны

Для обычной задачи не нужна "армия агентов".

Один основной исполнитель может сам читать исходники, реализовывать, исправлять обычные технические ошибки, проверять результат и собирать итог.

Отдельные помощники полезны для узких независимых работ: исследования, документации, анализа логов, точечного ревью или другой ограниченной задачи. Они не должны получать весь контекст без необходимости.

### 6. Методика не должна зависеть от конкретной модели и способа разработки 1С

Общие правила не должны быть привязаны к ChatGPT, Claude, Codex, Cursor, Copilot или другой конкретной модели.

То же относится к способу работы с 1С: EDT + MCP и XML + Конфигуратор - разные рабочие маршруты. Выбор зависит от того, где находятся реальные исходники и как конкретный проект уже развивается.

### 7. Простая задача должна оставаться простой

Если понятно, что нужно получить, где менять и как проверить - не нужны обязательное исследование, архитектурный документ и длинный план.

Выбираем самое простое проверенное решение, которое закрывает задачу без нарушения прав, данных и других существенных ограничений.

Если маленькая задача внезапно превращается в мини-фреймворк, универсальную подсистему или большой рефакторинг - стоит проверить, не создали ли сложность сами.

### 8. Методика должна выдерживать критику

Этот репозиторий не считается законченной теорией.

Полезны конкретные контрпримеры, Issues, Pull Request, эксперименты и реальные случаи, где правило мешает работе или существует более сильный стандартный механизм.

Хорошая воспроизводимая критика ценнее формального согласия. Методика должна улучшаться по фактам, а не защищать собственные правила как догму.


## Где ИИ экономит время - и где всё равно нужен контроль разработчика

Значительная часть времени разработчика и аналитика уходит не на набор кода, а на понимание входящей задачи, поиск нужного участка системы, изучение существующих механизмов, сравнение вариантов, проверки и подготовку понятного результата для других людей.

ИИ особенно полезен именно на этих участках.

### Разбор сырой постановки

ИИ может быстро разобрать:

- сообщения клиента или менеджера;
- переписку по задаче;
- ТЗ аналитика;
- расшифровку созвона;
- длинный поток мыслей и уточнений;
- смешанные требования и предположения о том, "как это лучше сделать".

Полезный результат здесь - не просто красивый пересказ, а отделение требуемого результата от предположенного механизма, явные неизвестные и вопросы, которые действительно нельзя получить из проекта самостоятельно.

### Анализ проекта, метаданных и исходников

Агент может:

- искать нужные объекты, модули, формы, запросы и места вызова;
- сопоставлять метаданные и код;
- восстанавливать цепочку обработки данных;
- находить существующие проектные механизмы;
- сравнивать текущее поведение с задачей;
- поднимать точные факты из большой кодовой базы без ручного обхода десятков файлов.

Это не отменяет необходимости проверять, что найден именно авторитетный источник проекта и правильный объект.

### Исследование и сравнение решений

Для одного неизвестного достаточно ограниченного поиска. Для действительно большой архитектурной или рискованной задачи ИИ может провести более широкий анализ:

- текущего проекта;
- документации и стандартов 1С;
- БСП и публичных API;
- web-источников;
- GitHub и доказанных реализаций;
- документации внешних API и интеграций.

Он может сопоставить несколько механизмов и примеров, показать ограничения и сократить часы ручного поиска. Решение всё равно должно опираться на проверяемые источники и реальные ограничения проекта, а не на уверенность модели.

### Документация и передача результата

ИИ хорошо снимает рутинную часть подготовки:

- отчётов о выполненной работе;
- инструкций пользователям;
- технической документации;
- чек-листов;
- описаний изменений;
- handoff-материалов для другого разработчика или команды;
- краткого итога для клиента, аналитика или руководителя.

Если история задачи и доказательства сохранены нормально, такие документы можно собирать из фактического состояния, а не восстанавливать по памяти.

### Реализация, ревью и проверки

ИИ может ускорять:

- типовые изменения кода;
- повторяющиеся операции;
- первичная проверка изменений;
- поиск очевидных дефектов и лишней сложности;
- подготовку и запуск точечных тестов;
- разбор логов и ошибок;
- исправление обычных технических проблем внутри уже понятной задачи.

При этом ИИ может уверенно ошибиться в API или метаданных, придумать лишнюю абстракцию, выбрать не тот слой, продублировать существующий механизм, потерять контекст или выдать статическую проверку за доказательство рабочего поведения.

Поэтому итоговое правило не меняется: **ИИ может сильно сократить время анализа и исполнения, но результат принимается по фактам - исходникам, проверкам, проверкам в работающей 1С и реальном интерфейсе и нужной человеческой приёмке.**

## Почему иногда полезно проверить решение до большой реализации

Проблема не в самом раннем написании кода. Проблема в цене поздно найденной ошибки.

После большой реализации дороже обнаружить, что:

- исходную задачу поняли не так;
- выбрали не тот объект, модуль или слой;
- в проекте или БСП уже был подходящий механизм;
- локальная доработка превратилась в ненужную универсальную систему;
- права/RLS, интеграционные последствия или поток данных обнаружились слишком поздно;
- никто заранее не определил, чем подтверждается результат.

Если задача затрагивает несколько связанных объектов, обмен, права, данные, миграцию или другой труднообратимый участок, разумно сначала снять именно те неизвестные, которые могут изменить решение.

Если небольшой эксперимент быстрее отвечает на технический вопрос, чем дальнейшие рассуждения, эксперимент - нормальный рабочий инструмент. Но эксперимент не становится принятой рабочей доработкой без обычной проверки и приёмки.

## Когда достаточно минимума

Методика не должна добавлять работу ради процесса.

**Задача очевидна и занимает несколько строк.**  
Не нужен отдельный архитектурный документ, исследование или длинный план. Достаточно коротко зафиксировать результат, границу и проверку - и делать.

**Агент умеет сам читать исходники, MCP-справку и документацию.**  
Не нужно вручную пересказывать технические факты, которые он может безопасно получить сам. Важно сохранить задачу, существенные решения, фактические проверки и итог.

**Опытный разработчик уже знает механизм.**  
Не нужно заставлять его искать дополнительные источники ради процесса. Проверяются только факты, которые реально могут изменить решение или которые нельзя надёжно держать в памяти.

**Небольшой прототип быстрее анализа.**  
Это нормальный путь для проверки технической гипотезы. Важно лишь отличать эксперимент от принятого результата.

**Не каждой доработке нужны одинаковые тесты и отчёты.**  
Глубина проверки кода, тестирования, проверки в работающей 1С и документации должна соответствовать риску и критериям задачи.

**Issue, PR и CI уже содержат подробности.**  
Не нужно дублировать их ещё в одной отчётной системе. Идея - одна короткая запись задачи и один короткий итог со ссылками на существующие доказательства.

## Как меняется глубина работы

Это не формальная классификация, которую нужно заполнять для каждой задачи.

| Ситуация | Достаточный путь |
|---|---|
| Результат, место изменения, механизм и проверка уже понятны | Короткая задача → реализация → точечная проверка → итог |
| Цель понятна, но неясно, где лучше реализовать; затронуто несколько объектов/модулей; нужен выбор между проектным и стандартным механизмом | Короткий план → текущий проект → БСП/стандартный публичный интерфейс → при необходимости один доказанный пример → реализация → проверка → итог |
| Есть несколько серьёзных вариантов; затрагиваются права/RLS, интеграции, миграция, широкий поток данных или труднообратимое решение | Исследование → сравнение вариантов → критика → решение → декомпозиция → реализация → усиленная проверка/приёмка → итог |

Поиск прекращается, когда найден ответ, достаточный для решения. Не нужно читать дополнительные источники только потому, что они доступны.

## История доработок - практическая ценность

Для долгоживущих 1С-систем потеря истории часто не менее болезненна, чем технический долг.

Через несколько лет в одной конфигурации могут накопиться изменения десятков специалистов. Старый подрядчик недоступен, документации нет, автор уже не помнит детали - и новая задача начинается с повторного разбора старого кода.

Сохранённая история должна позволять быстро восстановить:

- что просили изменить;
- какие объекты, модули, отчёты или обмены затронули;
- почему выбрали этот механизм, если решение было существенным;
- что сознательно не меняли;
- как проверили результат;
- что осталось неизвестным или ограниченным;
- какая версия или результат были приняты.

Если клиент через полгода спрашивает, что именно дорабатывали в документе, отчёте или обмене, ответ должен собираться из сохранённой истории, а не из повторного исследования исходников.

### У задачи должно быть и начало, и завершение

    пришла задача
    → поняли смысл
    → зафиксировали границы и проверку
    ...
    → получили изменение
    → реально проверили
    → приняли результат
    → сохранили короткий итог

Минимальный итог отвечает на пять вопросов:

- что сделано;
- где изменено;
- как проверено;
- что осталось неизвестным или ограниченным;
- какая версия или результат приняты.

Он не заменяет исходники, diff, тесты, CI или реальный запуск и не копирует их целиком. Это короткая точка входа в историю задачи.

## На что опирается подход

## Текущие рабочие маршруты и ограничения

Сейчас наиболее проработаны и реально используются два пути с Git:

- **1C:EDT + MCP** - когда канонические исходники находятся в EDT-проекте;
- **XML + Конфигуратор/CLI** - когда канонические исходники хранятся в XML.

Путь выбирается по источнику истины проекта, а не по тому, какой инструмент удобнее в конкретный момент.

### Подключение

Текущий режим - **ручная закреплённая копия / выборочное подключение с помощью агента**:

- пакет подключается закреплённой копией конкретной версии;
- существующие инструкции проекта сначала изучаются и сохраняются;
- можно подключать методику выборочно;
- автоматический безопасный установщик с обновлением и удалением пока не поставляется.

Актуальные детали: [Источники и подключение](docs/ru/SOURCES_AND_ADOPTION.md).

### Git и GitHub

Git + GitHub - рекомендуемый и наиболее проработанный маршрут: они дают точную историю задач, изменений, решений, PR и CI.

Общие контракты методики не требуют Git как единственно возможной архитектуры, но **готовый встроенный механизм долговременного состояния для работы без Git сейчас не поставляется**. Поэтому полный процесс без Git пока нельзя считать таким же готовым маршрутом, как EDT/XML с Git.

Если Git пока не используется, смотрите практический маршрут: [Работа без Git: что можно делать сейчас](docs/ru/NO_GIT.md).

## Обратная связь и Issues

Критика, ошибки, реальные контрпримеры и предложения приветствуются.

Перед созданием Issue прочитайте [правила обратной связи и оформления Issues](CONTRIBUTING.md). Особенно важно:

- сначала проверить, нет ли уже такой задачи;
- описывать проблему и ожидаемый результат, а не только предлагать конкретную реализацию;
- для технических утверждений по возможности прикладывать версию, источник, пример или воспроизводимый сценарий;
- не публиковать клиентские данные, закрытые исходники, ключи и другую конфиденциальную информацию;
- обсуждать решение, а не личности участников.

## Ограничения и статус

Методика:

- не заменяет разработчика 1С;
- не требует одинаковой глубины процесса для любой задачи;
- не утверждает, что её текущие правила единственно правильные или окончательные;
- не поставляет пока автоматический безопасный установщик с обновлением и удалением;
- не поставляет пока готовый встроенный механизм долговременного состояния для работы без Git.

До публичного v1.0.0 проект продолжает проверяться и упрощаться на реальных задачах.

> **Рабочий критерий:** каждый шаг должен либо помогать понять существенный риск, либо приблизить и доказать нужный результат, либо сохранить полезную историю принятой доработки. Иначе шаг лишний.
