# Глубокое многоэтапное исследование

Этот документ - для человека.

Точный навык для агента: [`1c-ai-deep-research`](../../.agents/skills/1c-ai-deep-research/SKILL.md).

## Когда оно вообще нужно

Большинство технических вопросов не требуют десятков источников.

Если надо узнать один метод, один реквизит или одну особенность версии, используется обычный точечный поиск.

Глубокое исследование нужно, когда цена ошибочного вывода выше:

- выбор архитектурного подхода;
- сравнение технологий;
- продуктовая гипотеза;
- противоречивые источники;
- дорогое решение, которое нельзя строить на двух случайных статьях.

## Три прохода

### V1 - собрать карту вопроса

Ориентир: 10-15 **новых уникальных достоверных источников**.

Сначала рассматривается текущий проект, если он относится к вопросу. Затем - первичные и официальные источники, исходные репозитории и только потом практика сообщества.

После первого прохода агент отдельно проверяет:

- где источники противоречат друг другу;
- каких данных не хватает;
- что пока остаётся предположением;
- какую альтернативу ещё надо проверить.

### V2 - проверить слабые места и альтернативы

Второй проход не повторяет первый.

Он ищет новые источники по слабым местам V1 и проверяет сильнейшую альтернативную трактовку.

Фиксируется:

- что пришлось исправить;
- какие выводы изменились;
- что осталось неизвестным;
- что нужно попытаться опровергнуть на следующем проходе.

### V3 - попытаться опровергнуть собственный вывод

Третий проход ищет:

- крайние случаи;
- несовместимость версий;
- ограничения;
- вопросы безопасности;
- реальные контрпримеры;
- причины, по которым выбранный вариант может не сработать.

После этого делается финальная критика и только затем формируется рекомендация.

Для задач по 1С:Фреш при необходимости добавляются актуальные официальные источники Фреш.

## 10-15 источников - ориентир, а не план по количеству

Нельзя искусственно добивать число:

- зеркалами;
- перепечатками;
- несколькими ссылками на один первоисточник;
- повторным чтением той же версии репозитория.

Если сильных источников всего семь, правильный результат - семь источников и честная отметка `SOURCE_LIMIT`.

## Что должно быть в результате

Нужно отделять:

- подтверждённый факт;
- наблюдение по текущему проекту;
- вывод;
- рекомендацию;
- неизвестное;
- ограничение по доступным источникам.

Рекомендация не становится фактом только потому, что её поддержало большинство просмотренных материалов.

## Где хранить исследование

Главный принцип:

> исследование должно переживать чат и иметь точную связь с задачей, ради которой оно выполнялось.

### Короткое одноразовое исследование

Итог можно сохранить прямо в долговременном состоянии задачи.

В рекомендуемом GitHub-процессе это Issue или конкретный комментарий.

### Исследование, которое пригодится снова

Тогда полезно сохранить отдельный документ в принятом проектом каталоге, например `docs/research/`, а в задаче оставить ссылку на него.

Не обязательно создавать отдельные файлы V1/V2/V3/FINAL только ради ритуала.

### Внешняя резервная копия

При необходимости можно сделать дополнительную копию во внешнем хранилище.

Она не должна незаметно становиться единственным источником истины.

## Кто может проводить исследование

Исследование не привязано к облаку или конкретной модели.

Его может выполнять:

- главный координатор;
- отдельный исследователь;
- локальный агент, которому передали узкий исследовательский вопрос;
- отдельная облачная исследовательская сессия.

Итог возвращается в долговременное состояние задачи и ответственному координатору/исполнителю.

В технических контрактах эти роли называются `Coordinator Main`, `OwningCoordinator` и `Local Main`.

## Что передавать обратно

Не нужно передавать координатору десятки полных страниц.

Достаточно:

- итоговых фактов;
- существенных противоречий;
- сильнейшего контраргумента;
- рекомендации;
- границ уверенности;
- оставшихся неизвестных;
- точных ссылок на источники и артефакт исследования.

## Когда глубокое исследование не нужно

Не используйте его для:

- обычной ошибки компиляции;
- поиска одного метода БСП;
- проверки одной версии;
- локального дефекта формы;
- ситуации, где текущий проект уже отвечает на вопрос.

Иначе исследование превращается в лишнюю работу.

## Коротко

```text
широкий дорогой вопрос
→ V1: карта + критика
→ V2: исправление + альтернативы
→ V3: попытка опровергнуть + финальная критика
→ компактный итог + точные источники
```

Если источников меньше ориентира - `SOURCE_LIMIT`, а не слабые ссылки ради количества.
