# Как превратить сырую мысль в нормальную задачу

Это не специальный ритуал для ИИ. Даже без ИИ полезно сначала понять, что именно нужно получить, проверить существующие механизмы и только потом менять код. ИИ просто делает часть этой работы быстрее.

Главное правило: не всякий разговор с ИИ уже является задачей на программирование. При этом не надо превращать каждую мелочь в большое проектирование.

Пользователю не нужно знать внутреннее название навыка: если методика загружена, агент сам должен распознать, когда нужен этот этап. Практические пользовательские формулировки собраны в [Как общаться с ИИ при разработке](AI_COMMUNICATION.md).

## Короткий путь

Если уже понятно, какой результат нужен, какова положительная граница задачи и как проверить результат, а существенных неизвестных нет - задача сразу идёт в работу. Явные запреты нужны только для реальных материальных границ. Механизм может быть уже известен или его точная техническая деталь может безопасно уточняться исполнителем по текущему проекту в рамках обычной работы.

```text
ясная задача
-> реализация
-> проверка
```

Никакого обязательного исследования или отдельного согласования плана здесь не нужно.

## Когда сначала надо сформулировать задачу

Это полезно, если исходный запрос надиктован голосом, представляет собой поток мыслей, смешивает желаемый результат с предположением "как это сделать", не содержит важного ограничения или оставляет реальный выбор поведения, архитектуры, данных или безопасности.

Тогда координатор один раз превращает разговор в компактную задачу. Исходный текст сохраняется только в разрешённом долговременном хранилище с учётом действующих правил доступа и конфиденциальности. Если такое сохранение требуется, но не разрешено или невозможно, это отдельный вопрос к владельцу задачи. Исполнителю по умолчанию передаётся не вся история разговора, а короткая задача.

## Режим уточнения задачи

Если мысль сложная, противоречивая или её проще надиктовать, можно написать:

```text
Помоги сначала уточнить задачу.
Задавай короткие вопросы по одному.
Технические факты, которые можешь проверить сам по проекту, у меня не спрашивай.
Когда информации достаточно - покажи короткую итоговую задачу.
```

Координатор сначала использует уже известное и задаёт только существенные вопросы. Если новый ответ противоречит прежнему решению, он должен явно уточнить, заменяет ли новое решение старое.

Это не обязательная анкета. Если задача уже понятна, режим уточнения не нужен.

## Предложенный человеком механизм - ещё не обязательное решение

Фраза вроде "наверное, тут надо вызвать такой-то метод" полезна как подсказка, но не становится архитектурным требованием автоматически. Сначала смотрим текущий проект и подтверждённые механизмы.

## Когда нужно исследование

Не исследуем всё подряд: один важный неизвестный факт - проверяем только его; широкий или высокорисковый вопрос - отдельное глубокое исследование; механизм уже доказан проектом - исследование не нужно.

## Когда нужен человек

Дополнительное решение человека нужно, если остаётся существенный выбор поведения продукта, архитектуры, безопасности/прав/данных, разрушительного действия или важного критерия приёмки. Обычные технические детали исполнитель решает самостоятельно внутри принятой задачи.

## Потеря чата не должна уничтожать проект

Существенная задача, решение или доказательство не должны существовать только внутри одного чата.

Для Git-проектов основной рекомендуемый путь: `репозиторий + точный SHA + Issue/задача + решения + доказательства`. Проект может работать и без Git/GitHub, но тогда ему всё равно требуется долговременное состояние с точными версиями и правилами конфликтов. Обычная общая папка не даёт автоматически историю и доказательность Git.

## Экономия токенов

Разговор, уточнение и публичное исследование разумно делать там, где это дешевле и удобнее. Дорогому исполнителю передаются только компактная задача, точные ссылки, ограничения и критерии проверки.

Во время обычной работы действует режим тишины: исполнитель не тратит выходные токены на описание каждого чтения файла, правки, запуска теста и внутреннего планирования. Он пишет промежуточно только при настоящем блокере или необходимости решения.

## Как агент общается с человеком

Человеку по умолчанию нужен короткий понятный ответ по-русски: что получилось, что важно решить и что делать дальше. Технические пакеты между агентами остаются компактными и англоязычными. Большие спецификации и отчёты хранятся один раз во внешнем долговременном состоянии, а в чат даётся ссылка.

## После реализации

Для существенного изменения полезна короткая карта результата: что поменялось, почему выбран этот механизм, что переиспользовано, какие объекты затронуты, что проверено и что осталось неизвестным.

Но это только помощь для проверки. Настоящие доказательства - исходники/diff, тесты, сборка, runtime/native-проверки и приёмка там, где они нужны.

## В двух строках

Ясную доказанную задачу - сразу делать.

Сырую задачу - один раз нормально сформулировать, исследовать только реальные пробелы, сохранить состояние вне чата и передать исполнителю компактный пакет.
