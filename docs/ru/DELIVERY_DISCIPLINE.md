# Простая задача должна оставаться простой

Этот документ отвечает на практический вопрос:

> сколько работы действительно нужно сделать, чтобы задача была решена хорошо - и когда пора остановиться?

Базовый путь:

```text
понятный результат
→ минимально достаточное изменение
→ проверка именно этого результата
→ готово
```

Это одинаково работает с ИИ и без него.

Точный машинный контракт: [`.1c-ai/core/DELIVERY_DISCIPLINE.md`](../../.1c-ai/core/DELIVERY_DISCIPLINE.md).

## Не начинайте с размера решения

Сначала определите результат.

Если человек говорит:

> Покажите остаток товара прямо в строке документа.

это не означает, что нужно проектировать новый слой остатков, общий сервис, кеш и отдельную подсистему.

Если текущий проект уже показывает:

- где находится форма;
- откуда берётся нужный остаток;
- какой механизм используется;
- как проверить результат,

задача идёт прямо в реализацию.

Реальный пример такого короткого пути есть в [кейсе быстрого пути](REAL_CASES.md#кейс-1-быстрый-путь-покажите-остаток-прямо-в-строке-документа).

## Когда достаточно сделать сразу

Короткий путь подходит, если одновременно понятны:

- наблюдаемый результат;
- область изменения;
- технический механизм уже известен или быстро определяется по текущему проекту;
- нет существенного выбора по данным, правам, архитектуре или бизнес-смыслу;
- понятно, чем проверить результат.

Тогда нормальный процесс выглядит так:

```text
короткая задача
→ исходники проекта
→ реализация
→ точечная проверка
→ итог
```

Не нужны отдельное исследование, длинный план и архитектурный документ только потому, что работу выполняет агент.

## Когда нужен короткий поиск по проекту

Иногда результат понятен, но технический путь ещё надо подтвердить.

Например:

> Сделайте отдельный отчёт по просроченным заказам.

До разработки разумно проверить, нет ли нужного результата уже в стандартном списке или отчёте.

Если текущий проект даёт ответ - поиск заканчивается. Возможно, код вообще не понадобится.

Такой случай показан в [кейсе проверки текущего проекта и штатного механизма](REAL_CASES.md#кейс-2-сначала-проверяем-проект-и-штатный-механизм-сделайте-отдельный-отчёт).

Практическое правило:

> Ищем ровно до тех пор, пока не получили факт, который позволяет принять решение.

Не нужно продолжать читать статьи, документацию и чужой код "для полноты", если текущий проект уже дал достаточный ответ.

## Когда задача сначала требует диагностики

Сообщение об ошибке - ещё не готовое техническое решение.

Например:

> После обновления платформы отчёт перестал открываться.

Сначала нужно:

1. воспроизвести проблему;
2. установить границу рабочей и нерабочей версии;
3. проверить, менялся ли сам отчёт;
4. локализовать причину;
5. только потом исправлять.

Не надо сразу реализовывать первую догадку пользователя или агента.

Такой поток показан в [кейсе с регрессией после обновления](REAL_CASES.md#кейс-3-support-после-обновления-отчёт-больше-не-открывается).

## Когда большая задача действительно большая

Есть задачи, которые нельзя честно сжать до одного изменения.

Например:

> Есть старая доработанная Бухгалтерия, свой блок и два обмена. Хотим вынести доработки в расширение и обновиться без потери данных.

Здесь проблема не в количестве строк будущего кода. Нужно сначала разобраться:

- какие доработки существуют;
- кто владеет данными;
- от чего зависят обмены;
- какие изменения обратимы;
- какой путь миграции допустим;
- как проверить и откатить результат.

После этого большая работа режется на отдельные проверяемые этапы.

См. [кейс большой задачи и декомпозиции](REAL_CASES.md#кейс-4-большая-задача-исследование-и-декомпозиция).

Важно: глубокое исследование выполняется для принятия действительно большого решения. Оно не должно автоматически переходить внутрь каждой последующей маленькой задачи.

## Положительная граница задачи

По умолчанию достаточно сказать, **что именно нужно изменить**.

Например:

```text
Цель:
показать согласованный остаток в строке товара.

Область:
только существующая форма и непосредственно необходимое получение/обновление остатка.

Проверка:
открыть форму и проверить значение в согласованном сценарии.
```

Не нужно перечислять половину документа в списке того, что "запрещено трогать".

Явный запрет нужен только для конкретной существенной границы: например, нельзя менять подписанный входящий документ, обходить RLS, трогать рабочую базу или изменять замороженный формат обмена.

Подробная корректировка этого правила ведётся в #137.

## Небольшой соседний шаг - не новая задача

Во время реализации исполнитель может обнаружить, что для результата нужно:

- поправить контекст выполнения;
- добавить одно поле в уже используемый запрос;
- скорректировать непосредственно связанный обработчик;
- исправить вызов метода;
- устранить ошибку компиляции или выполнения, появившуюся в изменяемом участке.

Если это не меняет бизнес-смысл, архитектуру, права, данные или критерий приёмки, это обычная часть реализации.

Не нужно возвращаться к человеку за разрешением на каждый такой шаг.

Вопрос нужен, когда обнаруженное изменение действительно меняет принятое решение.

## Когда обобщение оправдано

Новый общий механизм, вспомогательный слой или переработка кода имеют смысл, если есть конкретная причина:

- это прямо требуется задачей;
- такой механизм уже является принятой архитектурой проекта;
- без него нельзя корректно выполнить обязательный сценарий;
- есть несколько подтверждённых мест использования прямо сейчас;
- локальное решение создаёт реальную проблему безопасности или целостности.

Фраза "может пригодиться потом" сама по себе недостаточна.

## Сигналы, что задача начала раздуваться

Стоит остановиться и перепроверить границы, если:

- маленькая доработка внезапно создаёт несколько новых подсистем или слоёв;
- появляется большой рефакторинг, которого не требует результат;
- исследование продолжается после получения достаточного ответа;
- тестовая инфраструктура становится больше самой доработки;
- соседние улучшения начинают задерживать готовый результат;
- агент пытается сделать универсальный механизм вместо одного доказанного сценария.

Полезные вопросы:

1. Какой результат ждёт пользователь?
2. Что необходимо именно для него?
3. Что добавилось только ради "идеальности"?
4. Что можно вынести в отдельную задачу?

## Минимальность не означает халтуру

Сокращать нельзя то, что определяет корректность.

Нельзя ради скорости:

- обходить права/RLS;
- менять рабочую базу без разрешения;
- скрывать непроверенный факт;
- использовать внутренний метод БСП как стабильный публичный интерфейс без доказательства;
- пропускать проверку выполнения или проверку в реальном клиенте, если именно она нужна для утверждения о результате;
- выдавать статическую проверку за доказательство рабочего поведения.

Если задача затрагивает запросы, минимальность также не означает лишние чтения данных. 1С рекомендует [выбирать только действительно нужные поля и записи](https://its.1c.ru/db/content/v8std/src/300/200/i8100729.htm) и по возможности [объединять однотипные обращения](https://its.1c.ru/db/content/v8std/src/300/100/i8100436.htm).

Права/RLS остаются частью корректности и могут влиять на сформированные запросы и производительность - см. [стандарт 1С по условиям запросов и RLS](https://its.1c.ru/db/content/v8std/src/300/200/i8100658.htm).

## Когда задача закончена

Если согласованный результат получен и необходимые проверки пройдены - задача закончена.

Не надо после этого автоматически:

- переделывать соседний модуль;
- открывать новое исследование;
- "заодно" улучшать другой отчёт;
- обобщать локальный код;
- исправлять несвязанный дефект.

Нормальная схема:

```text
текущая задача = завершить
полезный соседний хвост = отдельная задача
```

## Что выглядит хорошим итогом

Для обычной небольшой задачи чаще всего достаточно:

- понятного результата;
- использования существующего проектного или стандартного механизма;
- небольшого ограниченного изменения;
- нужной проверки;
- точной версии результата;
- короткого итога.

Количество классов, абстракций, тестов и страниц документации само по себе не является показателем качества.

Метрики сложности могут быть сигналом для ревью, но не универсальным запретом. Например, BSL Language Server умеет считать [когнитивную](https://1c-syntax.github.io/bsl-language-server/diagnostics/CognitiveComplexity/) и [цикломатическую сложность](https://1c-syntax.github.io/bsl-language-server/diagnostics/CyclomaticComplexity/). Число помогает заметить сложный код, но само по себе не доказывает дефект.

## Коротко

- ясную маленькую задачу - делаем сразу;
- один технический неизвестный - проверяем только его;
- симптом - сначала диагностируем;
- большую рискованную работу - исследуем и делим на этапы;
- соседние технические исправления внутри принятого смысла исполнитель делает сам;
- обязательные проверки не сокращаем;
- после достижения результата останавливаемся.

Практические примеры всего потока: [Реальные 1С-задачи](REAL_CASES.md).
