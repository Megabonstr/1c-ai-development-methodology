# Структура проекта и база знаний

Этот документ - для человека.

Главный принцип:

> сначала держите проект маленьким и понятным; новые каталоги появляются только тогда, когда для них накопился отдельный устойчивый смысл.

Методика не требует специального большого дерева папок. Важно другое: не смешивать исходники, задачи, постоянные знания, доказательства и временные файлы.

## Обычный небольшой проект

Для старта достаточно примерно такой структуры:

```text
PROJECT_AI.md                     короткая карта проекта для агентов

src/ или EDT-проект               реальные исходники

docs/                             постоянная документация, если она уже нужна
sources/SOURCES.md                необязательно: реестр внешних источников/доноров

.1c-ai/                           установленный пакет методики
.agents/skills/1c-ai-*/           навыки методики

.tmp/1c-ai/                       необязательно: временные файлы, обычно gitignored
```

А состояние задач лучше не дублировать в папках проекта:

```text
GitHub Issue       задача, существенные решения, приёмка, итог
PR + commit        изменение исходников и точная версия
CI / artifact      результаты проверок и сгенерированные артефакты
```

Для маленького проекта обычно **не нужны** отдельные:

- `tasks/`;
- `notes/`;
- `plans/`;
- `reports/`;
- `evidence/`;
- `artifacts/`;
- `features/`.

Если в проекте уже есть хорошая собственная структура - сохраняйте её. Подгонять всё под одну схему не нужно.

## Что принадлежит методике, а что проекту

Методика управляет:

- `.1c-ai/**`;
- навыками `.agents/skills/1c-ai-*/**`;
- своими минимальными блоками подключения в файлах ИИ-клиентов.

Проекту принадлежат:

- реальные исходники 1С;
- `PROJECT_AI.md`;
- собственные инструкции и навыки;
- архитектура и документация;
- проектные правила;
- исследования и решения;
- тесты и настройки сборки и выпуска.

Не складывайте проектные знания внутрь `.1c-ai/`.

## PROJECT_AI.md - это карта, а не база знаний

`PROJECT_AI.md` нужен, чтобы агент быстро понял:

- что это за проект;
- где находятся настоящие исходники;
- EDT это или XML/Конфигуратор;
- какая версия проекта сейчас считается принятой;
- что нельзя менять;
- где лежат важные знания и правила;
- где живёт долговременное состояние задач;
- какие существенные UNKNOWN ещё открыты.

Хороший `PROJECT_AI.md` отвечает на вопрос:

> куда именно посмотреть по этой задаче?

Он не должен заставлять агента сканировать все `docs/**`, старые отчёты и исследования.

Пока прямых ссылок немного - указывайте файлы прямо.

Отдельный `INDEX.md` нужен только когда владельцев стало достаточно много и без индекса агенту уже трудно выбрать правильный.

Полный пример: [PROJECT_AI.example.md](../examples/PROJECT_AI.example.md).

## Куда класть разные виды информации

### Задача

Обычная задача живёт в трекере - в рекомендуемом GitHub-процессе это Issue.

Там же остаются:

- цель;
- границы;
- существенные решения;
- корректировки;
- критерии проверки;
- приёмка;
- короткий итог.

Не нужно копировать ту же задачу ещё и в `tasks/`.

Если проект сознательно использует spec-as-code, спецификация может жить в репозитории, но это уже отдельный проектный контракт, а не обязательное правило методики.

### План

План одной задачи обычно живёт вместе с задачей.

Отдельный файл имеет смысл, если это уже план нескольких задач, большой инициативы, миграции или развёртывания.

Тогда в долгоживущем проекте может появиться, например:

`docs/plans/`

Но создавать его заранее не нужно.

### Постоянные знания

Архитектура, устройство подсистем, интеграции, правила данных, рабочие инструкции и другие повторно используемые знания живут в обычной документации проекта.

Например:

```text
docs/architecture/
docs/integrations/
docs/warehouse/
docs/ux/
```

Лучше группировать знания по реальному предмету проекта, чем плодить универсальные папки ради классификации.

### Исследования

Если исследование нужно только одной задаче - достаточно сохранить его результат и ссылки в этой задаче.

Если результат будут использовать снова - его стоит сохранить в репозитории, например:

`docs/research/`

Такое исследование должно оставаться доказательством и источником решения, а не вторым владельцем архитектуры.

### Решения

Обычное решение внутри одной задачи остаётся в Issue.

Если решение влияет на много будущих задач и должно жить годами, проект может завести ADR/decision-каталог, например:

`docs/decisions/`

Старое решение не надо молча переписывать. Лучше явно указать, чем оно заменено.

### Правила и инструкции

Здесь полезно различать две вещи:

- **инструкция** говорит, куда идти и как работать;
- **правило/политика** говорит, что обязательно должно оставаться истинным.

Например, `PROJECT_AI.md` может направлять агента в проектный документ по RLS, но не должен копировать весь этот документ внутрь себя.

Если проект большой, может появиться, например:

`docs/engineering/`

Но существующие `AGENTS.md`, `CLAUDE.md`, собственные docs/rules и другие рабочие владельцы можно сохранить.

### Отчёты

Обычный итог задачи лучше оставить в Issue.

Отдельный файл-отчёт нужен, когда он имеет самостоятельную ценность:

- для клиента;
- поддержки;
- аудита;
- передачи другой команде;
- будущего повторного использования.

Тогда возможен, например:

`docs/reports/`

### Доказательства

Доказательство и отчёт - не одно и то же.

- тестовый run;
- CI job;
- artifact;
- hash;
- runtime/native проверка -

это доказательства.

Отчёт только объясняет, что они подтверждают.

По умолчанию доказательства лучше хранить там, где они возникли: PR, CI, artifact store, Issue.

Отдельный `docs/evidence/` нужен только если проекту действительно требуется долговременный audit-набор в Git.

### Сгенерированные артефакты

EPF/ERF/CFE, сборки, выгрузки и другие сгенерированные файлы не становятся исходниками.

Обычно:

- промежуточные сборки - локально и игнорируются;
- CI-сборки - в CI artifacts;
- принятые дистрибутивы - в Release/package/archive.

В задаче хранится точная ссылка, версия или hash результата.

### Временные файлы

Логи, кеши, debugger output, временные выгрузки и промежуточные сборки не являются базой знаний.

Используйте уже принятый временный каталог проекта.

Если его нет - можно использовать игнорируемый:

`.tmp/1c-ai/`

Черновая заметка тоже не должна жить годами: полезную часть перенесите в задачу, решение, план, документацию или доказательство; остальное удалите.

## Как структура растёт в долгоживущем проекте

Проект не обязан сразу становиться таким:

```text
docs/
  architecture/
  engineering/
  research/
  decisions/
  plans/
  reports/
  evidence/
  roadmap/
  integrations/
```

Это только пример того, что **может** появиться со временем.

Нормальная последовательность такая:

1. сначала `PROJECT_AI.md` и несколько прямых ссылок;
2. затем обычные `docs/` по реально возникшим темам;
3. если исследования начали повторно использоваться - `docs/research/`;
4. если появились долговечные решения для нескольких задач - `docs/decisions/`;
5. если есть несколько связанных инициатив - `docs/plans/` или roadmap;
6. если отчёты/аудит действительно нужно хранить в Git - соответствующий каталог;
7. индекс появляется только когда прямые ссылки перестали работать удобно.

То есть структура растёт **из реальной нагрузки**, а не из шаблона.

## Почему не стоит копировать дерево одного рабочего проекта

В одном долгоживущем рабочем 1С-проекте естественно появились `notes`, `plans`, `reports`, `evidence`, `tasks`, `artifacts`, `rules`, `instructions` и другие каталоги.

Это полезный опыт, но в нём же видно, как со временем смыслы могут начать пересекаться:

- рабочий план может оказаться в `notes` и `plans`;
- отчёт о проверке - в `reports` или `evidence`;
- markdown-доказательство - внутри `artifacts`;
- файл задачи - повторять активный Issue.

Поэтому методика не предлагает копировать это дерево.

Она предлагает сначала определить **что это за информация и кто её владелец**, а уже потом выбирать путь.

## Как привести существующий проект в порядок без большой миграции

Не нужно переносить всё сразу.

### 1. Сначала классифицируйте

Для существующих файлов достаточно понять:

- это задача?
- постоянное знание?
- правило?
- исследование?
- решение?
- план?
- отчёт?
- доказательство?
- сгенерированный артефакт?
- временный файл?

### 2. Укажите текущих владельцев

Добавьте в `PROJECT_AI.md` точные ссылки на уже существующие файлы/индексы.

На этом этапе ничего переносить не обязательно.

### 3. Перестаньте создавать новые дубли

Новые задачи - в систему задач.  
Новые постоянные знания - в docs.  
Временные заметки - локально.  
Сборки - в local/CI/Release.

### 4. Старое переносите только когда оно снова понадобилось

Если старый `notes/рабочий план.md` снова используется - тогда решите, это task plan или cross-task plan.

Если `artifacts/evidence.md` фактически является доказательством или отчётом - перенесите при следующем изменении.

Нет пользы в массовой перестройке только ради красивого дерева.

## EDT и XML равноправны

Эта структура не требует EDT.

Если реальные исходники - EDT-проект, используется EDT-путь.

Если проект ведётся в XML и собирается Конфигуратором/CLI, используется XML-путь.

Структура знаний от этого не меняется.

## Если проект работает без Git/GitHub

Смысл классов остаётся тем же: задача, знания, решения, доказательства, артефакты и временные файлы всё равно должны быть разделены.

Но текущая граница методики сохраняется: [Gitless design](../research/GITLESS_LOCAL_STATE_V1.md) описан, а рабочий механизм writer/replay/lock/snapshot/recovery ещё не поставляется.

Gitless сейчас - `DESIGNED_DEGRADED_COMPATIBILITY`.

Использовать такой путь можно только поверх уже работающего проектного долговременного носителя. Папка `tasks/` сама по себе не превращает файловую историю в эквивалент Git/Issue/PR.

Практический маршрут без Git: [Работа без Git: что можно делать сейчас](NO_GIT.md).

Собственный автоматизированный механизм долговременного состояния пока не поставляется и остаётся будущим направлением развития.

## Что не надо хранить в Git

По умолчанию не помещайте туда:

- пароли и токены;
- рабочие базы;
- локальные настройки компьютера;
- тяжёлые промежуточные сборки;
- кеши IDE;
- случайные логи;
- временные временные файлы отладки и выполнения.

Резервные копии информационных баз и клиентских данных требуют отдельной политики безопасности.

## Резервное копирование

Обычная схема Git-проекта:

```text
локальная рабочая копия
+
основной Git-сервер
```

При необходимости можно добавить независимый третий слой:

- второй Git-сервер;
- `git bundle`;
- версионируемый архив;
- S3/NAS/облачный диск.

Резервная копия не становится источником истины или доказательством runtime-поведения только потому, что файл в ней существует.

## Коротко

Для маленького проекта:

- исходники остаются там, где они уже живут;
- `PROJECT_AI.md` - короткая карта;
- повторно используемые знания - в обычных docs;
- задачи - в Issue;
- доказательства - в PR/CI/artifacts;
- временное - локально.

Для долгоживущего проекта:

- новые каталоги появляются только когда соответствующий тип информации реально повторяется;
- `PROJECT_AI.md` указывает точных владельцев;
- дубли не создаются;
- старые файлы мигрируют постепенно, когда их снова трогают.

Главное - **семантический владелец, а не название папки**.
