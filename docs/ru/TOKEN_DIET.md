# Экономия контекста и токенов

Этот документ - для человека.

Главная цель: **дорогой исполнитель должен получать только то, что реально помогает выполнить текущую задачу**.

Экономить нужно и входные, и выходные токены. Но нельзя экономить за счёт важных ограничений, рисков и доказательств.

## Практическая схема

Если есть дешёвый или фиксированный по цене координатор/исследователь, используйте его для:

- обсуждения сырой идеи;
- уточнения задачи;
- публичного поиска по 1С/БСП/документации;
- сравнения вариантов;
- подготовки компактной задачи.

Дорогому исполнителю передавайте:

- точную задачу;
- необходимые ограничения;
- точные ссылки/пути;
- уже найденные доказательства;
- критерии проверки.

```text
разговор / исследование
→ компактная долговременная задача
→ дорогой исполнитель
→ минимальное изменение + нужные проверки
```

Это рекомендация по экономике, а не требование использовать конкретного провайдера.

## 1. Не загружать всё заранее

Плохой подход:

```text
весь README
+ все Issue
+ все навыки
+ вся история чатов
+ весь проект
+ старые исследования
→ исполнитель
```

Хороший подход:

```text
точная задача
→ нужный владелец правила
→ один нужный навык/профиль
→ конкретные исходники
→ конкретные доказательства
```

Расширяйте контекст только когда текущего действительно не хватает.

## 2. Передавать ссылки, а не копии

Лучше передать:

- ссылку на задачу;
- точный путь к файлу;
- SHA/версию;
- имя метода/раздела;
- ссылку на результат исследования;
- идентификатор теста/сборки.

Хуже - копировать один и тот же длинный текст между чатами и агентами.

## 3. Исследование хранить один раз

Если вопрос уже качественно исследован и вывод принят:

- сохраните результат в долговременном состоянии;
- передавайте следующему агенту точную ссылку;
- не заставляйте нового исполнителя заново читать десятки публичных источников.

Повторное исследование нужно только при конкретном новом противоречии или существенном неизвестном факте.

## 4. Исправление передавать только дельтой

Если исполнитель сделал почти всё правильно, не отправляйте ему исходную задачу заново.

Достаточно:

```text
Что неверно:
<конкретный дефект>

Доказательство:
<точная ссылка / файл / проверка>

Что изменить:
<минимальная дельта>

Что перепроверить:
<критерий>
```

## 5. Режим тишины

Для дорогого исполнителя по умолчанию действует **режим тишины**.

Не нужно тратить выходные токены на сообщения:

- "сейчас читаю файл";
- "проверяю метод";
- "вношу изменение";
- "запускаю тест";
- "исправил ещё одну ошибку".

Обычные чтения, правки, сборки, тесты и технические исправления выполняются без пошагового рассказа.

Промежуточное сообщение нужно только если:

- требуется решение человека;
- найден существенный блокер;
- важный неизвестный факт меняет путь работы;
- действительно нужна передача работы между контекстами.

В остальных случаях - один короткий итог.

## 6. Большие отчёты не копировать в чат

Подробный технический отчёт, лог или доказательство, если он вообще нужен:

1. сохраняется один раз во внешнем долговременном месте;
2. получает точную ссылку/идентификатор;
3. в чат возвращается короткий итог и ссылка.

Это особенно важно для дорогих моделей с высокой стоимостью выходных токенов.

## 7. Чат не является долговременной памятью проекта

Контекст может закончиться. Сессия может исчезнуть. Провайдер или модель могут поменяться.

Поэтому новый агент должен восстанавливать работу из:

- карты проекта;
- долговременной задачи;
- точной версии исходников;
- принятых решений;
- ссылок на доказательства.

А не из пересказа умершего чата.

Для Git-проекта обычно это `PROJECT_AI.md + Issue/задача + SHA + evidence handles`.

Для проекта без Git нужны другие точные идентификаторы состояния. Гарантии истории при этом могут быть слабее.

## 8. Не экономить на существенном

Нельзя выкинуть ради токенов:

- бизнес-ограничение;
- `DO_NOT_TOUCH`;
- требования по правам/RLS;
- критерий приёмки;
- материальный риск;
- обязательную проверку;
- неизвестный факт, который реально влияет на решение.

Экономия начинается с **шума и повторов**, а не с нужной информации.

## Плохо / хорошо

### Плохо

Пользователь надиктовал длинную мысль → весь голосовой текст отправили дорогому исполнителю → исполнитель сам повторно исследует БСП → комментирует каждый шаг → после ошибки ему снова присылают всю историю.

### Хорошо

Координатор один раз:

1. сохраняет исходный запрос там, где это разрешено;
2. выделяет нужный результат и ограничения;
3. проверяет один неизвестный факт;
4. сохраняет компактную задачу.

Исполнитель получает только задачу и точные ссылки, работает в режиме тишины и возвращает короткий результат.

## Короткое правило

> Думать, обсуждать и исследовать можно широко. Исполнять - по компактной задаче. Повторно не платить за уже известное.
