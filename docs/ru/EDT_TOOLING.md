# EDT: практический набор инструментов для разработки 1С с ИИ

Этот файл - для человека.

Он отвечает на практический вопрос:

> Я работаю в 1C:EDT. Что мне действительно нужно кроме самой EDT, что полезно добавить, а что ставить только под конкретную задачу?

Проверено по первичным источникам 19 сентября 2026 года. Совместимость плагинов зависит от конкретной линии EDT; если первичный источник не подтверждает вашу версию явно, ниже стоит `UNKNOWN / проверить для своей EDT`.

Главное правило: **не устанавливайте весь каталог плагинов "на всякий случай"**. Дополнительный плагин должен закрывать конкретную потребность и не становиться скрытой обязательной частью методики.

## Четыре разных слоя

Важно не смешивать четыре вещи:

```text
1C:EDT
  ↓
плагины / проверки / тестовые инструменты
  ↓
EDT-MCP - структурированные операции ИИ-агента в EDT
  ↓
1c-ai-development - процесс, роли, источники, границы задач и доказательства
```

- **EDT** владеет проектной моделью, редакторами, сборкой, метаданными и стандартными механизмами IDE.
- **Плагины и проверки** добавляют диагностики, тестовый интерфейс, БСП-подсказки, импорт/экспорт и другие узкие возможности.
- **EDT-MCP** даёт агенту структурированный доступ к операциям EDT. Он не заменяет статические проверки, тестовый движок или правила разработки.
- **1c-ai-development** определяет, как сформулировать задачу, какие источники считать авторитетными, кто выполняет работу и какое доказательство действительно подтверждает результат.

Сбой или отсутствие опционального плагина не делает методику неработоспособной.

## Что именно доказывают проверки и инструменты

Зелёный результат у разных инструментов означает разное:

- [`dt-project-checks`](https://github.com/1C-Company/dt-project-checks) проверяет **структурную целостность EDT-проекта**. Его PASS не доказывает корректность бизнес-логики.
- [`v8-code-style`](https://github.com/1C-Company/v8-code-style) - официальный инструмент 1С для статических проверок BSL, метаданных, форм, прав и запросов по стандартам 1С. Это **STATIC**-доказательство: оно не заменяет сборку, запуск, пользовательский сценарий или приёмку.
- [BSL Language Server](https://1c-syntax.github.io/bsl-language-server/diagnostics/) - независимый community-анализатор с настраиваемыми диагностиками; часть диагностик отключена по умолчанию. Он полезен как дополнительный STATIC-слой, но не является владельцем официальных стандартов 1С и может требовать проектной настройки.
- [YAxUnit](https://bia-technologies.github.io/yaxunit/) выполняет тесты и проверяет описанные в них утверждения. Зелёный тест доказывает только покрытый сценарием/утверждениями результат; UI, production-данные, права/RLS и пользовательская приёмка не становятся доказанными автоматически.
- [EDT-MCP](https://github.com/DitriXNew/EDT-MCP) даёт агенту доступ к операциям и наблюдаемому состоянию EDT. Успешный MCP-вызов доказывает только результат конкретной операции; например, валидация запроса проверяет синтаксис/семантику в контексте проекта, но не его производительность и не бизнес-корректность.

Подробная модель уровней доказательств: [Как понимать проверки результата](EVIDENCE_MODEL.md).

## Короткий выбор

### Минимум

Для обычного EDT-проекта достаточно:

```text
1C:EDT
+ реальный EDT-проект и его настоящие исходники
+ локальный исполнитель
+ стандартные проверки, уже поставляемые с вашей EDT
```

Если для исполнения выбран профиль **EDT + MCP**, добавляется:

```text
+ EDT-MCP
```

EDT-MCP не является обязательным для всех пользователей методики: он нужен тогда, когда локальный исполнитель должен работать через структурированные операции EDT/MCP.

### Рекомендуемое

Для большинства проектов стоит **использовать уже поставляемые с EDT официальные проверки**, а не начинать с установки сторонних пакетов:

- **1С:Стандарты разработки V8 / v8-code-style** - проверки кода, метаданных, форм, прав и запросов;
- **1С:EDT Project checks / dt-project-checks** - структурная целостность EDT-проекта;
- **YAxUnit** - если проект реально использует модульные автоматические тесты.

### Опциональное

Добавляйте только под конкретную потребность:

- BSL Language Server через EDT-коннектор - дополнительные BSL-диагностики;
- 1C:SSL support - помощь в БСП-проектах;
- EDT CF-builder - импорт/экспорт CF/CFE;
- EDT Test Runner - интерфейс запуска YAxUnit из EDT;
- каталоги и готовые наборы плагинов - для поиска/удобной установки, но не как источник истины о совместимости каждого компонента.

## Что поставить в типичном новом проекте

### Вариант 1 - обычная EDT без управления IDE через агента

```text
EDT
+ встроенные v8-code-style / dt-project-checks
+ YAxUnit, если нужны модульные тесты
```

Дополнительные плагины - только после появления конкретной потребности.

Система контроля версий проекта (например, Git) полезна и рекомендуется, но это отдельный слой процесса и не входит в обязательный набор EDT-плагинов.

### Вариант 2 - EDT + локальный исполнитель через MCP

```text
EDT
+ встроенные v8-code-style / dt-project-checks
+ EDT-MCP
+ YAxUnit, если нужны модульные тесты
```

В этом варианте EDT-MCP уже умеет получать список проблем EDT и описания проверок и запускать YAxUnit. Поэтому установка BSL LS connector или EDT Test Runner должна давать **дополнительную** пользу разработчику, а не дублировать уже доступный запуск тестов агентом.

## Как решать, нужен ли ещё один плагин

Перед установкой задайте пять вопросов:

1. Какую конкретную проблему он решает?
2. Есть ли эта возможность уже в EDT или EDT-MCP?
3. Есть ли первичный источник с установкой для моей точной линии EDT?
4. Подтверждена ли лицензия у первичного проекта?
5. Могу ли я удалить плагин без изменения архитектуры проекта?

Если на вопросы 2-4 нет ясного ответа, плагин не должен становиться частью базового набора.

## Совместимость: как читать этот гайд

Три разных утверждения нельзя смешивать:

- **"репозиторий активен"** - означает только, что проект изменяется;
- **"целевой файл сборки (`source target`) указывает EDT X"** - подтверждает направление сборки исходников, но не гарантирует опубликованный совместимый бинарный пакет;
- **"первичный проект явно заявляет/проверяет EDT X"** - наиболее сильное публичное доказательство совместимости из документации проекта.

Поэтому в этом гайде не выводится совместимость только из даты последнего коммита.

## Первичные источники

Проверка выполнена 19.09.2026. Для version-sensitive утверждений выше использованы первичные владельцы, а не каталоги/агрегаторы:

- [EDT-MCP upstream](https://github.com/DitriXNew/EDT-MCP) - capability и заявленная совместимость EDT;
- [v8-code-style](https://github.com/1C-Company/v8-code-style) и [dt-project-checks](https://github.com/1C-Company/dt-project-checks) - официальные 1С EDT-проверки;
- [BSL Language Server diagnostics](https://1c-syntax.github.io/bsl-language-server/diagnostics/) - community STATIC-анализ;
- [YAxUnit documentation](https://bia-technologies.github.io/yaxunit/) - тестовый движок, утверждения и способы запуска.

Точные релизы меняются быстрее этой страницы. Перед установкой сверяйте `latest release`/README первичного проекта и линию вашей EDT/платформы; каталог плагинов сам по себе не является доказательством совместимости.
