# Что это за репозиторий и как он работает

Если коротко, этот репозиторий - не готовая конфигурация 1С, не плагин и не отдельный AI-разработчик.

Это **пакет методики разработки с ИИ**, в котором соединены три вещи:

1. **знания для человека** - как ставить задачи, выбирать решения, не переусложнять разработку, проверять результат и сохранять историю;
2. **машинные инструкции для агента** - правила, маршруты и навыки, по которым агент работает внутри реального проекта;
3. **источник подключения методики** - агент может взять этот репозиторий, сравнить его с правилами вашего проекта и после разрешения подключить нужные части.

То есть репозиторий одновременно является **базой знаний** и **устанавливаемым набором инструкций для AI-агента**.

## Что именно подключается к проекту

Основной машинный пакет находится здесь:

```text
.1c-ai/
.agents/skills/1c-ai-*/
```

В проект также может добавляться короткая карта `PROJECT_AI.md`, которая говорит агенту:

- где находятся реальные исходники;
- какой способ разработки используется;
- где искать проектные правила и документацию;
- где хранится состояние задач;
- на какую версию проекта опираться.

Методика не должна заменять уже работающие правила проекта вслепую. Перед подключением агент сначала сравнивает существующий процесс с этим репозиторием.

Результатом сравнения может быть:

- ничего не менять;
- взять только отдельные части;
- подключить пакет целиком.

Подробнее: [как сравнить и подключить методику](SOURCES_AND_ADOPTION.md).

## Что происходит после подключения

В самом общем виде:

```text
человек даёт задачу
->
агент понимает, достаточно ли она ясна
->
при необходимости уточняет только существенное
->
смотрит текущую конфигурацию, код и готовые механизмы
->
формирует короткую исполнимую задачу
->
вносит изменение
->
проверяет результат подходящим способом
->
сохраняет короткий итог и точную версию
```

Если задача простая и механизм уже понятен, большая часть промежуточных шагов просто пропускается.

Если задача большая или рискованная, методика добавляет исследование, сравнение вариантов, декомпозицию и более серьёзную проверку.

## Где здесь человек, а где агент

Человек отвечает прежде всего за то, **что должно получиться**, и за существенные решения, которые нельзя вывести из исходников.

Агент должен самостоятельно:

- читать исходники и метаданные;
- искать уже существующие механизмы;
- проверять документацию и примеры, когда это действительно нужно;
- выбирать место технической реализации внутри принятой задачи;
- писать и исправлять код;
- запускать доступные проверки;
- возвращать понятный результат.

Идея не в том, чтобы человек заранее расписал агенту каждый технический шаг.

## Зачем отдельные машинные файлы

Человеческие документы объясняют смысл и дают общую картину.

Машинные файлы нужны, чтобы агент **действительно следовал этим правилам**, а не просто прочитал красивый README.

Например, они определяют:

- что агент читает первым;
- когда задача готова к реализации;
- когда исследование не нужно;
- как экономить контекст;
- как выбирать исходники и стандартные механизмы;
- какие проверки что доказывают;
- когда агент должен спросить человека;
- что сохранить после завершения работы.

Человеку обычно не нужно читать `.1c-ai/**`.

## Это не конкретный способ разработки 1С

Методика старается отделять общие правила от конкретных инструментов.

Сейчас наиболее проработаны два маршрута:

- 1C:EDT + MCP;
- XML-исходники + Конфигуратор.

Но репозиторий не является оболочкой только над EDT или только над MCP.

Инструменты могут меняться, а основные правила - понятная задача, повторное использование готовых механизмов, ограниченное изменение, проверка и история результата - остаются.

## Git и GitHub

Git + GitHub сейчас являются наиболее полным и рекомендуемым маршрутом, потому что дают:

- точную версию исходников;
- историю задач и решений;
- ветки и изменения;
- проверки CI;
- возможность вернуться к принятому состоянию.

Работа без Git допускается только если проект уже имеет другой надёжный способ хранить состояние задач и версии исходников.

Техническое исследование возможного собственного Gitless-механизма находится в `docs/research/GITLESS_LOCAL_STATE_V1.md`, но это **дизайн, а не готовая функция**.

Для человека есть отдельная практическая инструкция: [Работа без Git: что можно делать сейчас](NO_GIT.md). Технический исследовательский документ для обычной работы читать не требуется.

## Что этот репозиторий НЕ делает

Он не:

- генерирует готовую конфигурацию по одной фразе;
- заменяет знания 1С;
- заставляет использовать конкретную модель;
- требует отдельного агента на каждый этап;
- требует глубокого исследования для каждой задачи;
- гарантирует правильность результата только потому, что код написал ИИ.

Это скорее **рабочая среда правил и знаний**, которую можно дать способному агенту, чтобы он работал в реальном 1С-проекте более последовательно и предсказуемо.

## Если хотите попробовать

Самый короткий путь:

1. откройте [Быстрый старт](GETTING_STARTED.md);
2. дайте агенту ссылку на этот репозиторий и доступ к своему проекту только на чтение;
3. попросите сначала сравнить существующие правила и ничего не менять;
4. после оценки разрешите минимальное подключение;
5. дайте первую небольшую реальную задачу.

Если сначала хотите увидеть логику работы на примерах: [реальные 1С-задачи](REAL_CASES.md).

Если хотите понять, где что хранится: [структура проекта и база знаний](PROJECT_STRUCTURE.md).
