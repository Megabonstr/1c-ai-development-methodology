# Работа без Git: что можно делать сейчас

Git - рекомендуемый путь, но методика не требует, чтобы каждый 1С-проект уже был переведён на Git.

Без Git можно использовать постановку задач, поиск существующих механизмов, работу агента с исходниками, проверки и короткую историю результата.

Главное ограничение: **этот репозиторий пока не поставляет собственный готовый механизм хранения истории задач и версий исходников без Git**.

Поэтому сегодня работа без Git опирается на то, что уже есть в вашем проекте.

## Вариант 1. Git нет, но есть трекер и хранилище с историей

Например, у вас уже есть:

- Jira, YouTrack, Bitrix24, Redmine, Notion или другой трекер;
- общая папка или облачное хранилище с историей версий;
- EDT-проект или XML-выгрузка конфигурации;
- резервные копии базы или выгрузки конфигурации.

Тогда можно работать примерно так:

```text
задача в существующем трекере
->
агент читает текущие исходники
->
при необходимости фиксируется снимок состояния до изменения
->
агент выполняет задачу
->
проверяется результат
->
в задаче сохраняется:
что сделано
как проверено
какая версия или снимок приняты
что осталось неизвестным
```

Вместо commit SHA используется та идентификация версии, которая реально есть у проекта:

- номер релиза или сборки;
- дата и имя выгрузки;
- архив исходников;
- резервная копия;
- версия документа в корпоративном хранилище;
- другой стабильный идентификатор.

Это слабее Git, но намного лучше, чем хранить историю только в чате.

## Вариант 2. Git нет, есть только локальный проект или Конфигуратор

Так тоже можно работать, но история будет заметно слабее.

Минимально разумный порядок:

1. определить, где находятся текущие исходники;
2. перед существенным изменением сохранить отдельный снимок состояния;
3. завести долговременную запись задачи;
4. дать агенту текущие исходники и эту задачу;
5. после изменения сохранить новый снимок или выгрузку;
6. записать результат и проверки.

Например:

```text
Задача:
Исправить ...

Исходное состояние:
Config_2026-09-19_1200.zip

Результат:
Config_2026-09-19_1430.zip

Проверено:
...

Ограничения:
...
```

Снимок не обязан быть ZIP. Это может быть выгрузка XML, копия EDT-проекта, файл CF, резервная копия или другой принятый способ проекта.

Важно одно: потом должно быть понятно, **какое состояние было до задачи и какое было принято после неё**.

## Вариант 3. Нет Git, трекера и истории версий вообще

В этом случае методику всё равно можно использовать для самой разработки:

- разобрать задачу;
- проверить существующий код и механизмы;
- не переусложнять решение;
- реализовать;
- проверить.

Но полный долговременный цикл будет неполным.

Если единственная история существует только в чате, в памяти разработчика, в одной постоянно перезаписываемой папке или в рабочей базе без сохранённых снимков, после потери контекста нельзя надёжно восстановить, что именно было принято раньше.

Это нужно честно считать ограничением, а не делать вид, что такой процесс эквивалентен Git.

## Что обязательно нужно для долговременного no-Git маршрута

Чтобы no-Git процесс считался не просто удобной текущей работой, а восстановимым долговременным маршрутом, у проекта должны быть четыре вещи:

- **устойчивая идентификация задачи и состояния исходников** - должно быть понятно, к какой задаче и к какой версии/снимку относится результат;
- **явное право на запись** - должно быть понятно, кто имеет право менять долговременную запись задачи и принятое состояние;
- **один писатель или реальное правило разрешения конфликтов** - две параллельные записи не должны молча перетирать друг друга;
- **честно более слабое происхождение версий** - архив, выгрузка или номер версии не нужно выдавать за Git-историю, если её нет.

Если хотя бы одного из этих условий нет, отдельные части методики всё равно можно использовать для постановки, разработки и проверки. Но полный долговременный цикл нужно считать `UNKNOWN/BLOCKED`, а не эквивалентом Git.

## Что дать агенту

Для проекта без Git агенту достаточно коротко указать:

```text
Исходники:
<где лежит EDT-проект / XML / другой источник>

Текущее состояние:
<номер версии / архив / снимок / UNVERSIONED_CURRENT_STATE>

Задачи:
<где хранится долговременная запись>

Проверки:
<как обычно проверяется результат>

Резервные копии:
<где и как фиксируются, если применимо>
```

Если проект уже использует свой трекер, инструкции или папку документации, методика должна использовать их, а не создавать параллельную систему без причины.

## Что теряется без Git

Без Git обычно слабее:

- точное сравнение до и после;
- история отдельных изменений;
- ветки для параллельной работы;
- происхождение конкретной версии;
- проверка изменений через diff;
- удобный откат;
- связь Issue -> PR -> commit -> CI.

Поэтому Git остаётся рекомендуемым вариантом для долгоживущей разработки.

Но отсутствие Git не означает, что нужно отказаться от остальных полезных частей методики.

## Что пока не готово

В репозитории есть технический дизайн собственного долговременного механизма для работы без Git: `docs/research/GITLESS_LOCAL_STATE_V1.md`.

Но это **исследование и проектирование, а не готовая функция**.

Пакет пока не умеет сам автоматически:

- вести локальный журнал задач;
- блокировать параллельную запись;
- создавать снимки;
- восстанавливать состояние после сбоя;
- заменять Git полноценной локальной историей.

Разработка такого механизма остаётся отдельным будущим направлением.

## Самый простой совет

Если Git пока не используется:

1. не останавливайте из-за этого работу;
2. используйте уже существующий трекер или долговременный документ для задач;
3. сохраняйте идентифицируемое состояние исходников до и после существенных изменений;
4. храните короткий итог и проверки вместе с задачей;
5. считайте происхождение и историю изменений более слабыми, чем при Git;
6. при росте проекта отдельно рассмотрите переход на Git.
