# Как заранее уточнить цель 1С-задачи

Этот документ - для человека.

Технический контракт для агента: [`.1c-ai/profiles/1c-common/TASK_PREFLIGHT.md`](../../.1c-ai/profiles/1c-common/TASK_PREFLIGHT.md).

## Зачем это нужно

В 1С пользовательское название поля не всегда совпадает с реальным реквизитом, путём данных или местом выполнения кода.

Но **человеку не нужно заранее знать технический путь данных (DataPath), точные типы и клиент/серверный контекст**, если их можно установить по исходникам.

Человек должен хорошо описать смысл задачи. Техническую привязку агент обязан доказать по проекту.

## Что должен сказать человек

Для большинства задач достаточно трёх вещей:

```text
Что должно произойти:
<наблюдаемый результат>

Границы задачи:
Только <какой объект/поведение относится к задаче>
и прямо необходимая связанная реализация.
Сохранить остальное существующее поведение.

Как проверить:
<реальный сценарий>
```

Если есть реальная рискованная граница, добавьте её отдельно и коротко. Не нужно перечислять все соседние поля только потому, что они не относятся к задаче.

### Нейтральный пример

```text
Что должно произойти:
В форме документа после смены Склада пересчитать доступный остаток для строк Товары и показать его в существующей колонке формы.

Границы задачи:
Только отображение доступного остатка для текущих строк и прямо необходимая связанная реализация.
Не менять проведение документа и складские данные.

Как проверить:
Открыть документ с несколькими товарами, сменить Склад и убедиться,
что доступный остаток пересчитался для всех строк, а документ и данные учёта не изменились.
```

Этого достаточно, чтобы начать техническую проверку цели.

## Что должен установить агент

По реальным исходникам агент при необходимости определяет:

- какой элемент формы связан с задачей;
- какой реальный путь данных используется (`DataPath`);
- какой объект/реквизит владеет данными;
- точный тип;
- клиентский или серверный контекст;
- одно это значение или коллекция;
- событие/действие, где изменение должно происходить;
- фактический источник значения.

Если эти факты уже прямо зафиксированы в задаче и доказаны - повторно исследовать их не нужно.

Место реализации тоже подтверждается по смыслу и исходникам. Официальные стандарты 1С различают поведение отдельного объекта, связанную с типом объекта "статическую" функциональность и общую функциональность в [модулях объекта, менеджера и общих модулях](https://its.1c.ru/db/content/v8std/src/400/300/i8100486.htm); логика, нужная только конкретной форме, относится к [модулю формы](https://its.1c.ru/db/content/v8std/src/1%C2%A0200/700/i8100630.htm). Это помогает проверить выбранное место, но не отменяет архитектуру текущего проекта.

## Почему нельзя угадывать по подписи на форме

На экране может быть написано "Доступный остаток", а реальное значение может находиться:

- в реквизите объекта;
- в реквизите формы;
- в текущей строке таблицы;
- в составном типе;
- в динамическом списке;
- в вычисляемом представлении.

Поэтому команда "измени колонку Доступный остаток" ещё не доказывает технический путь изменения.

## Сначала положительная граница задачи

Главная граница обычной задачи - **что именно мы меняем**, а не список всего остального проекта.

Для большинства задач достаточно:

```text
Границы задачи:
Только <цель/объект задачи> и прямо необходимая связанная реализация.
Сохранить остальное существующее поведение.
```

Явный `DO_NOT_TOUCH` нужен только при реальном риске, когда исполнитель может правдоподобно задеть важную соседнюю границу.

Например:

```text
DO_NOT_TOUCH:
- рабочая база
```

или конкретное юридически значимое значение, которое соседний механизм не должен перезаписать.

Не превращайте обычную правку формы в перечень `Организация / Склад / Валюта / Цена / ...`. Положительная граница уже означает, что эти поля не являются целью изменения.

## Если нужной цели нет

Агент не должен автоматически:

- создавать новый реквизит;
- подменять его похожим;
- выбирать первый подходящий элемент;
- расширять метаданные.

Если требуемый объект/поле не найдено и от этого зависит смысл задачи - это существенный неизвестный факт. Нужно остановиться или запросить решение в соответствии с задачей.

Если для решения нужен стандартный механизм, агент должен проверить именно поддерживаемый интерфейс, а не считать любой `Экспорт` стабильным API. В стандарте структуры модуля 1С отдельно выделен [программный интерфейс](https://its.1c.ru/db/content/v8std/src/400/100/i8100455.htm), а в официальной документации БСП есть [глава "Программный интерфейс"](https://its.1c.ru/db/content/bsp321doc/src/index.htm). Конкретный метод и его сигнатуру всё равно нужно сверять с версией проекта.

## Если есть фильтр или список

Для динамических списков и отчётов важно сохранить смысл фильтрации:

- какое поле фильтруется;
- каким оператором;
- что означает пустое значение;
- фильтр действует на сервере или после получения данных.

Но и здесь человек формулирует **ожидаемое поведение**, а техническую реализацию агент подтверждает по проекту.

Если задача затрагивает выборку данных, полезно отдельно проверить, что запрос получает только необходимые поля и записи - это соответствует [официальным рекомендациям 1С по оптимальным запросам](https://its.1c.ru/db/content/v8std/src/300/200/i8100729.htm). Если на те же данные действуют права/RLS, их нельзя считать отдельной "последующей" темой: разные RLS-условия могут менять формируемые запросы и их производительность, что прямо отмечено в [стандарте 1С по условиям запросов и RLS](https://its.1c.ru/db/content/v8std/src/300/200/i8100658.htm). Это не повод обходить права ради скорости.

## Коротко

Человек отвечает за:

- бизнес-смысл;
- наблюдаемый результат;
- границы;
- проверку.

Агент отвечает за доказанную техническую привязку этого смысла к реальным объектам 1С.
