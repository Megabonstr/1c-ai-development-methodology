# 1C:EDT + MCP - что это и когда использовать

Этот документ - для человека.

Точный технический профиль для агента: [`.1c-ai/profiles/1c-edt-mcp/PROFILE.md`](../../.1c-ai/profiles/1c-edt-mcp/PROFILE.md).

## Что такое EDT

**1C:Enterprise Development Tools (EDT)** - среда разработки 1С, в которой конфигурация представлена как проект с моделью метаданных, модулями, формами, запросами, проверками и механизмами сборки.

Git часто используется рядом с EDT для истории исходников, но сама методика не требует конкретного Git-хостинга для выбора EDT-пути.

## Что такое MCP

**MCP (Model Context Protocol)** позволяет ИИ-агенту работать через структурированные инструменты вместо догадок о внутреннем формате проекта.

Для EDT-пути эта методика использует как основной внешний проект [DitriXNew/EDT-MCP](https://github.com/DitriXNew/EDT-MCP).

Upstream EDT-MCP на 19.09.2026 заявляет поддержку **EDT 2026.1 и 2026.2** одним артефактом; E2E и protocol-conformance проверки проекта выполняются на EDT 2026.2. Latest release на момент проверки - [v2.17.1](https://github.com/DitriXNew/EDT-MCP/releases/tag/v2.17.1). Для более новой/другой линии EDT совместимость нужно перепроверять по текущему upstream README/релизам.

## Кто за что отвечает

`1c-ai-development` и EDT-MCP решают разные задачи:

- **1c-ai-development** - границы задачи, роли, Source First, экономия контекста, требуемые проверки и честная интерпретация доказательств;
- **EDT-MCP** - технический доступ агента к операциям и наблюдаемому состоянию EDT.

Upstream EDT-MCP сейчас предоставляет, среди прочего:

- информацию о проектах и конфигурации;
- список ошибок/предупреждений EDT и описания проверок;
- BSL-навигацию, чтение/изменение модулей и анализ вызовов;
- content assist и платформенную документацию;
- проверку запросов в контексте проекта;
- инспекцию форм;
- операции с метаданными;
- запуск/обновление приложения и отладку;
- запуск и отладку YAxUnit.

Полный каталог инструментов быстро меняется, поэтому эта страница не дублирует его. Источник истины - [текущий upstream EDT-MCP](https://github.com/DitriXNew/EDT-MCP) и live help установленного сервера.

## Что именно доказывает EDT-MCP

Сам факт успешного MCP-вызова **не доказывает корректность доработки**.

Примеры:

- `get_project_errors`/problem summary показывают наблюдаемые diagnostics EDT и установленных проверок; отсутствие ошибок не означает, что бизнес-сценарий работает;
- query validation проверяет синтаксис/семантику запроса в проектном контексте, но не доказывает производительность на реальных данных;
- изменение метаданных/модуля подтверждает выполненную операцию, но не сборку и не runtime-поведение;
- screenshot/layout формы показывает состояние редактора/модели формы, но не автоматически доказывает пользовательский сценарий в клиенте;
- запуск YAxUnit через MCP даёт **TEST**-доказательство только для реально выполненных тестов и утверждений.

Для смысла уровней SOURCE/STATIC/TEST/BUILD/DEPLOY/RUNTIME/NATIVE смотрите [Модель доказательств](EVIDENCE_MODEL.md).

## EDT checks: что приходит агенту

Важно различать два официальных класса проверок 1С:

- [1C-Company/dt-project-checks](https://github.com/1C-Company/dt-project-checks) проверяет **структурную целостность EDT-проекта**;
- [1C-Company/v8-code-style](https://github.com/1C-Company/v8-code-style) выполняет статические проверки BSL, метаданных, форм, прав и языка запросов по стандартам 1С.

Оба инструмента входят в соответствующие поставки EDT; `v8-code-style` upstream указывает включение начиная с EDT 2021.3 и публикует версию 0.8.0 для EDT 2026.2.

EDT-MCP может получить проблемы/описания проверок из EDT, но **не становится владельцем смысла этих диагностик**. Структурная проверка, code-style diagnostic и runtime-тест доказывают разные вещи.

## YAxUnit через EDT/MCP

[YAxUnit](https://bia-technologies.github.io/yaxunit/) - отдельный тестовый движок 1С с утверждениями, тестовыми данными и отчётами. Он не является частью EDT-MCP.

EDT-MCP умеет запускать/отлаживать YAxUnit через свой execution surface. Это удобный способ получить результат тестового прогона, но зелёный YAxUnit означает только то, что прошли конкретные выполненные тесты/утверждения.

Отдельно учитывайте важную оговорку upstream YAxUnit для режима запуска из EDT **без перезапуска 1С:Предприятия**: в запущенное приложение передаётся только текст текущего тестового модуля; изменения других модулей/конфигурации требуют перезапуска/обновления. См. [документацию запуска YAxUnit](https://bia-technologies.github.io/yaxunit/docs/getting-started/run/).

## Когда выбирать EDT + MCP

Путь подходит, если:

- канонические исходники проекта ведутся в EDT;
- команда реально работает через EDT;
- изменения должны проходить через модель EDT;
- доступна совместимая версия EDT-MCP;
- агенту нужны структурированные операции над проектом/метаданными/BSL/формами.

Если канонический источник - XML и сборка идёт через Конфигуратор/CLI, используйте [XML + Конфигуратор](XML_CONFIGURATOR.md).

## Как выглядит техническая работа

Например, нужно добавить реквизит документа и заполнить его на форме.

```text
получить зафиксированную задачу
→ локальный исполнитель открывает точный EDT-проект
→ проверяет объект, типы и текущий механизм
→ через EDT-MCP выполняет разрешённое изменение
→ запускает релевантные STATIC/TEST/BUILD-проверки
→ при необходимости обновляет базу и запускает реальный сценарий
→ при необходимости проверяет настоящий клиент/UI
→ возвращает точную версию результата и evidence handles
```

Как задача хранится, ветвится и принимается - отдельный слой процесса. Рекомендуемый Git/GitHub-вариант: [Git и GitHub: как ведётся задача](GIT_GITHUB_FLOW.md).

## Почему не редактировать внутреннее представление в обход EDT

Если каноническим источником является EDT-проект, предпочтение у операций, согласованных с моделью EDT.

Ручная правка внутренних файлов/представлений может обойти model-aware операции и затруднить проверку целостности. Если нужной операции через выбранный инструмент нет, обходной путь должен быть выбран явно и после него нужны соответствующие проверки проекта - это решение профиля/задачи, а не универсальный запрет на любой файловый edit.

## Что всё равно решает Coordinator / Human Owner

EDT-MCP не определяет бизнес-семантику.

До Local Main должны быть заморожены, когда они материальны:

- какой результат нужен;
- что нельзя менять;
- продуктовые/архитектурные/data/safety решения;
- acceptance meaning;
- required gates.

Дешёвые технические факты Local Main/Coordinator проверяют через source/tools сами; человека спрашивают только там, где реально требуется решение или authority.

## Какие дополнительные инструменты ставить

Не устанавливайте плагины "по списку".

Для обычного EDT-проекта сначала используйте возможности EDT и официальные проверки. YAxUnit добавляйте, когда проекту нужны автоматические тесты. BSL Language Server и другие инструменты подключайте только если они дают конкретный дополнительный сигнал.

Практический список с границами доказательств и совместимости: [EDT: набор инструментов](EDT_TOOLING.md).
