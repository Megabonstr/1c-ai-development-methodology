# Гайд для новичка: от обычного 1С-разработчика до первой задачи с ИИ

Этот документ можно читать линейно. Он рассчитан на разработчика 1С, который умеет работать с конфигурацией, но ещё не обязан знать Git workflow, MCP, агентные роли и внутренние термины этой методики.

Если хочется **сразу попробовать**, используйте [быстрый старт](GETTING_STARTED.md).

## 1. Что ИИ здесь делает

ИИ - сильный помощник для:

- поиска по проекту;
- чтения документации;
- сравнения стандартных механизмов;
- написания и изменения кода;
- проверки diff;
- запуска доступных инструментов и тестов.

Но он не знает автоматически:

- что именно имел в виду пользователь;
- где в вашем проекте источник истины;
- какой механизм уже принят в проекте;
- что нельзя менять;
- действительно ли результат работает в 1С.

Поэтому нормальный процесс остаётся инженерным:

```text
понять задачу
→ посмотреть реальные исходники
→ использовать существующий/стандартный механизм
→ изменить минимум
→ проверить
```

Если убрать ИИ, этот процесс всё равно имеет смысл. ИИ просто делает часть шагов быстрее.

## 2. Что нужно минимально

Для первого запуска нужны:

1. реальные исходники вашего проекта 1С;
2. ИИ-клиент/агент, который умеет работать с файлами проекта;
3. место, где задача и решения переживут чат;
4. способ проверить результат.

Не нужно сразу устанавливать все MCP, тестовые фреймворки и плагины из экосистемы.

## 3. Обычный чат и агент - не одно и то же

Чат хорошо обсуждает задачу.

Агент умеет дополнительно работать с файлами, Git, IDE, MCP, CLI и другими инструментами - если они ему доступны.

В методике встречаются две логические роли:

- **координатор** - помогает сформулировать задачу, держит важные решения и ссылки;
- **исполнитель** - работает с реальными исходниками и доводит техническую часть до проверки.

Для маленькой задачи это может быть один и тот же агент.

## 4. EDT + MCP или XML + Конфигуратор

Выбирайте не по моде, а по источнику истины.

### EDT + MCP

Подходит, если рабочие исходники проекта находятся в 1C:EDT и именно EDT-проект считается каноническим.

MCP - это способ дать агенту доступ к операциям инструмента через стандартизированный интерфейс.

### XML + Конфигуратор/CLI

Подходит, если проект хранит исходники в XML и собирается/загружается через Конфигуратор или командную строку.

Оба пути поддерживаются. Не надо одновременно делать оба каноническими без явного решения проекта.

## 5. Зачем Git и GitHub

**Git** хранит историю и даёт точный идентификатор версии исходников.

**GitHub** удобно хранит задачи, обсуждения, Pull Request и результаты CI.

Это рекомендуемый путь, потому что новый агент может продолжить работу от точных ссылок даже после потери старого чата.

Но GitHub не является обязательным. Без него нужно другое разрешённое долговременное хранилище задач и точная идентификация состояния исходников. Оно может иметь более слабые гарантии истории.

## 6. Что такое PROJECT_AI.md

Это короткая карта проекта для агента.

Пример:

```text
Project: My1CProject
AuthoritativeSource: EDT project ./My1CProject
ExecutionProfile: .1c-ai/profiles/1c-edt-mcp/PROFILE.md

DO_NOT_TOUCH:
- production infobase
- unrelated metadata

OpenMaterialUnknowns:
- none
```

Смысл:

- где реальные исходники;
- как с ними работать;
- что особенно нельзя ломать;
- какие важные вопросы пока не решены.

Не превращайте этот файл в историю всех задач.

## 7. Первая задача

Возьмите маленький, наблюдаемый результат.

Хорошо:

> После выбора Контрагента заполнить существующий ОсновнойДоговор. Организацию и Склад не менять.

Плохо:

> Посмотри весь модуль, улучши архитектуру, сделай красиво и заодно почини всё подозрительное.

У задачи должны быть:

- один результат;
- границы;
- способ проверки.

Если вы не знаете точный механизм - это нормально. Не надо его придумывать. Агент сначала посмотрит проект и стандартные механизмы.

Например, при выборе места для кода можно опираться на официальное разделение ответственности [модуля объекта, менеджера и общих модулей](https://its.1c.ru/db/content/v8std/src/400/300/i8100486.htm) и [модуля формы](https://its.1c.ru/db/content/v8std/src/1%C2%A0200/700/i8100630.htm). Если задача типовая и проект использует БСП, сначала стоит проверить её [официальную документацию БСП, включая главу "Программный интерфейс"](https://its.1c.ru/db/content/bsp321doc/src/index.htm), а не придумывать параллельный API.

Если задача связана с большой выборкой, циклом чтения данных или правами, не используйте упрощённые правила вроде "запросы в цикле всегда запрещены". 1С рекомендует [выбирать только нужные данные](https://its.1c.ru/db/content/v8std/src/300/200/i8100729.htm) и по возможности [объединять однотипные обращения](https://its.1c.ru/db/content/v8std/src/300/100/i8100436.htm), но описывает исключения; RLS при этом остаётся частью корректности и может влиять на формируемые запросы и производительность ([стандарт 1С](https://its.1c.ru/db/content/v8std/src/300/200/i8100658.htm)).

## 8. Что написать агенту

Вам не нужно знать названия внутренних навыков и вручную выбирать `task-framing`, `research` или `implementation`. Если агент прочитал инструкции методики, **маршрут он должен выбрать сам по смыслу вашей просьбы**.

После подключения методики для готовой задачи достаточно короткого запроса:

```text
Прочитай инструкции проекта и PROJECT_AI.md.
Работай по задаче <точный идентификатор>.
Не выходи за её границы.
Сначала проверь реальные исходники и стандартные механизмы,
затем внеси минимальное изменение и выполни нужные проверки.
```

Если задача пока сырая, надиктована голосом или вы сами не уверены в формулировке, можно попросить: **"Помоги сначала уточнить задачу. Задавай короткие вопросы по одному."**

Практические фразы для исследования, реализации, review, коррекции, продолжения и остановки собраны отдельно: [Как общаться с ИИ при разработке](AI_COMMUNICATION.md).

Подробнее о превращении сырой мысли в исполнимую задачу: [Формулирование задачи](TASK_FRAMING.md).

## 9. Как понять, что всё действительно работает

У разных проверок разный смысл.

- код прочитан/проверен статически - ещё не значит, что он выполняется;
- тест прошёл - значит прошёл конкретный тест;
- сборка успешна - ещё не значит, что форма работает;
- реальный запуск подтверждает поведение в runtime;
- пользовательский интерфейс иногда нужно проверить в настоящем клиенте;
- финальное бизнес-поведение может требовать приёмки человеком.

Техническая модель: [Модель доказательств](EVIDENCE_MODEL.md).

## 10. Что чаще всего ломает процесс

- огромный промпт вместо одной задачи;
- неотмеченная смена решения: сначала сказали одно, потом противоположное, но не указали, что старое правило отменено;
- единственная копия важного решения в чате;
- выдуманный API вместо проверки проекта/БСП;
- глубокое исследование очевидной задачи;
- весь репозиторий загружен "на всякий случай";
- дорогой исполнитель комментирует каждый технический шаг;
- "скомпилировалось" выдано за "работает";
- попутный рефакторинг вне задачи;
- установка всех плагинов сразу без реальной необходимости.

## 11. Что делать после первой задачи

Сначала повторите тот же небольшой цикл ещё раз.

Потом открывайте только нужные документы:

- [Проверенные источники](SOURCE_FIRST.md) - если агент изобретает лишнее;
- [Экономия токенов](TOKEN_DIET.md) - если дорого и много контекста;
- [Простая задача должна оставаться простой](DELIVERY_DISCIPLINE.md) - если задачи разрастаются;
- [Оркестрация](ORCHESTRATION.md) - если появились несколько контекстов/агентов;
- [Навыки](SKILLS.md) - если хотите понимать маршрутизацию;
- [EDT + MCP](EDT_MCP.md) или [XML + Конфигуратор](XML_CONFIGURATOR.md) - для технического пути.

А для первого практического запуска теперь переходите в [быстрый старт](GETTING_STARTED.md).
