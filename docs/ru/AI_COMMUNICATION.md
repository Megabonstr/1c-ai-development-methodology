# Как общаться с ИИ при разработке

Эта страница - не сборник "магических промптов".

Современная модель обычно понимает обычную человеческую речь, голосовую диктовку, сокращения и даже довольно шумный поток мыслей. Но чем больше в разговоре повторов, смешанных тем и противоречивых решений, тем больше контекста агенту приходится заново разбирать и тем выше риск, что он выберет не тот смысл.

Главная цель - не писать как робот и не сокращать каждую фразу до минимума.

> **Говорите естественно, но делайте текущий смысл однозначным.**

## Вам не нужно знать названия навыков

Если методика подключена и агент прочитал инструкции проекта, он должен **сам выбрать нужный маршрут**.

Пользователю не нужно помнить названия:

- `1c-ai-task-framing`;
- `1c-ai-source-first-research`;
- `1c-ai-bounded-implementation`;
- `1c-ai-focused-review`;
- других внутренних навыков.

Достаточно обычными словами сказать, чего вы хотите сейчас.

Названия навыков полезны разработчикам методики и опытным пользователям для диагностики, но не являются пользовательским интерфейсом.

## Два разных режима общения

### Когда вы обсуждаете и думаете

Можно:

- думать вслух;
- диктовать голосом;
- рассматривать варианты;
- менять гипотезу;
- добавлять контекст постепенно;
- писать разговорно.

Не надо превращать каждую реплику в формальную постановку задачи.

### Когда начинается исполнимая задача

Перед изменением кода или данных должен остаться один текущий смысл:

- что хотим получить;
- границы задачи;
- существенные ограничения;
- как поймём, что результат подходит;
- что пока действительно неизвестно.

Координатор должен убрать из рабочего пакета:

- уже отменённые варианты;
- повторённую историю;
- словесный шум, который ничего не меняет;
- несколько несвязанных задач;
- старое решение, если вы его позже заменили.

Локальный исполнитель получает компактную текущую задачу, а не весь разговор.

## Самая опасная проблема - не лишние слова, а противоречия

Например:

> Делай только короткие ответы.

Через несколько сообщений:

> Когда обсуждаем варианты, можно отвечать подробнее.

Обе фразы сами по себе нормальны. Проблема появляется, если неясно, вторая фраза **дополняет** первую или **заменяет** её.

Если вы изменили решение, полезно сказать прямо:

```text
Коррекция:
предыдущее правило про короткие ответы отменяем для обсуждения.
В обсуждении можно подробно.
Для итоговой рабочей задачи - кратко.
```

Или ещё проще:

```text
Я изменил решение: X больше не действует. Теперь делаем Y.
```

Если агент видит материальное противоречие и не может честно определить приоритет, он должен уточнить, а не угадывать.

## Как сделать сообщение понятнее

Не обязательно использовать шаблон, но полезно разделять разные типы информации.

Например:

```text
Факт:
после добавления цены в отчёт по остаткам одна и та же номенклатура стала появляться несколькими строками.

Хочу получить:
сохранить исходную детализацию отчёта и показывать одну актуальную цену для каждой строки.

Моя идея, но не обязательное решение:
возможно, цену нужно получать из последнего среза регистра цен.

Вопрос:
проверь по проекту источник цены и уровень детализации данных, затем выбери минимальный корректный способ изменить запрос.
```

Так модель не перепутает вашу гипотезу с обязательным техническим решением.

## Если вы не уверены - так и напишите

Плохо:

```text
Создай регистр и храни там остатки.
```

если вы на самом деле знаете только бизнес-цель.

Лучше:

```text
Нужно получить такой результат: ...
Я не уверен, нужен ли для этого отдельный регистр.
Сначала проверь текущий проект и стандартные механизмы, затем предложи минимальный вариант.
```

Не заставляйте себя придумывать техническое решение только ради "хорошего промпта".

## Голосовая диктовка - нормальный вход

Голосом часто быстрее объяснить сложную ситуацию.

Нормальный путь:

```text
голос / поток мыслей
→ координатор выделяет смысл
→ при необходимости задаёт несколько коротких вопросов
→ фиксируется компактная задача
→ исполнитель работает уже по ней
```

Полную расшифровку не нужно каждый раз отправлять исполнителю.

## Что написать агенту

Ниже - обычные человеческие формулировки. Внутренний навык агент должен выбрать сам.

| Если вы хотите | Можно написать |
|---|---|
| Сначала разобраться в сырой мысли | **"Помоги сначала уточнить задачу. Задавай мне короткие вопросы по одному. Когда смысла достаточно - покажи итоговую задачу."** |
| Проверить один неизвестный технический вопрос | **"Сначала проверь этот вопрос по текущему проекту и нужным источникам. Код пока не меняй."** |
| Провести более широкое исследование | **"Сначала нужно исследование и сравнение вариантов. Реализацию пока не начинай."** |
| Выполнить уже понятную задачу | **"Задача уже сформулирована. Работай по ней. Обычные технические детали выясняй сам."** |
| Проверить готовое изменение | **"Не меняй код. Проверь этот diff/PR и найди реальные дефекты, лишний объём и неподтверждённые допущения."** |
| Проверить результат | **"Проверь только то, что требуется этой задачей, и скажи, что реально подтверждено, а что осталось неизвестным."** |
| Продолжать после обычной технической ошибки | **"Продолжай в рамках той же задачи. Обычные ошибки исправляй сам. Спрашивай меня только если меняется смысл, архитектура, данные, права или критерий результата."** |
| Изменить прежнее решение | **"Коррекция: прежнее X отменяем. Теперь Y."** |
| Продолжить старую задачу | **"Продолжаем Issue/задачу <идентификатор>. Новая дельта только такая: ..."** |
| Остановить работу | **"Стоп. Ничего больше не меняй. Зафиксируй текущее состояние, результат и неизвестные."** |

Это примеры, а не обязательный синтаксис.

## Режим уточнения задачи

Если мысль сложная, противоречивая или её проще надиктовать, можно явно попросить:

```text
Перейди в режим уточнения задачи.
Задавай короткие вопросы по одному.
Технические факты, которые можешь проверить сам по проекту, у меня не спрашивай.
Когда информации достаточно - покажи короткую итоговую задачу.
```

В этом режиме хороший координатор:

1. сначала выделяет то, что уже понятно;
2. задаёт только первый существенный вопрос;
3. не спрашивает у вас пути, типы, API и другие факты, которые может проверить сам;
4. при необходимости предлагает несколько понятных вариантов;
5. если новый ответ противоречит старому решению - уточняет, заменяет ли новое решение старое;
6. прекращает вопросы, как только задача достаточно понятна для следующего шага.

Это не анкета и не допрос.

## Если что-то пошло не по плану

Не нужно заново пересказывать всю задачу.

Если проблема техническая:

```text
Продолжай ту же задачу.
Исправь техническую проблему сам и перепроверь результат.
```

Если вы меняете смысл:

```text
Коррекция:
раньше было X.
X отменяем.
Теперь нужно Y.
Остальная задача без изменений.
```

Если вы просто добавляете ограничение:

```text
Дополнение:
результат тот же.
Новое существенное ограничение: ...
```

Так агенту не приходится угадывать, что именно изменилось.

## Не повторяйте то, что уже надёжно сохранено

Если задача уже есть в Issue, документе или другом долговременном носителе, лучше написать:

```text
Продолжаем Issue #123.
Коррекция только такая: ...
```

чем снова вставлять всю историю обсуждения.

Это снижает стоимость контекста и уменьшает риск, что старая версия задачи случайно станет выглядеть актуальной.

## Сленг, шутки и разговорный стиль

Они не запрещены.

Проблема не в самом слове-паразите или шутке. Проблема начинается, когда они:

- скрывают текущую просьбу;
- смешивают несколько задач;
- делают непонятным, какое решение сейчас действует;
- без необходимости переносятся в рабочий контекст следующих агентов.

Профессиональная цель - **ясный текущий смысл**, а не стерильный язык.

## Короткое правило

> **Обсуждать можно широко. Решения меняйте явно. Исполнять - по компактному текущему смыслу.**

Если исходный запрос уже ясен, никакой дополнительный "режим уточнения" не нужен.
