# Как выбирать решения и источники

Этот документ - для человека.

Точный машинный контракт: [`.1c-ai/core/SOURCE_FIRST.md`](../../.1c-ai/core/SOURCE_FIRST.md).

## Главный принцип

Не придумывать новый механизм, пока не проверено, что подходящего решения уже нет в проекте или стандартной 1С.

Это обычная профессиональная привычка разработчика, а не отдельная "защита от ИИ". ИИ только снижает стоимость поиска и сравнения.

## Порядок поиска

### 1. Текущий проект

Сначала смотрим реальные исходники проекта.

Именно там находятся:

- фактические типы и метаданные;
- текущая версия конфигурации;
- уже принятые соглашения;
- существующие похожие реализации.

Если вопрос касается того, **где должна жить логика**, это тоже лучше не угадывать. Официальные стандарты 1С различают ответственность [модуля объекта, модуля менеджера и общих модулей](https://its.1c.ru/db/content/v8std/src/400/300/i8100486.htm), а для логики конкретной формы отдельно задают [правила модулей форм](https://its.1c.ru/db/content/v8std/src/1%C2%A0200/700/i8100630.htm). Это ориентир вместе с архитектурой текущего проекта, а не требование механически переносить старый код.

### 2. Стандартный механизм 1С и БСП

Если задача типовая, ищем поддерживаемый стандартный механизм.

Например:

- файлы;
- пользователи;
- дополнительные реквизиты;
- печать;
- фоновые задания;
- уведомления;
- контактная информация.

Если у БСП есть подходящий **публичный программный интерфейс**, предпочтение у него.

Это опирается не только на нашу методику: официальная документация БСП содержит отдельную [главу "Программный интерфейс"](https://its.1c.ru/db/content/bsp321doc/src/index.htm), а стандарт 1С различает [программный интерфейс модуля и внутреннюю реализацию](https://its.1c.ru/db/content/v8std/src/400/100/i8100455.htm). Но конкретный метод всё равно проверяется по версии БСП и исходникам проекта.

### 3. Внутренний код БСП - как пример, а не как стабильный API

Иногда полезная логика находится во внутренней процедуре.

Её можно изучить, чтобы понять алгоритм.

Но служебный метод нельзя автоматически считать стабильным внешним интерфейсом.

Если публичного API нет, нужную идею можно адаптировать в собственном коде проекта.

Для запросов действует та же логика: сначала проверяем фактическую задачу, а не применяем лозунг. Официальные рекомендации 1С советуют [выбирать только действительно нужные данные](https://its.1c.ru/db/content/v8std/src/300/200/i8100729.htm) и по возможности [не выполнять множество однотипных запросов по одному объекту](https://its.1c.ru/db/content/v8std/src/300/100/i8100436.htm), при этом прямо описывают допустимые исключения. Если доступ зависит от ролей/RLS, права остаются частью корректности: условия RLS могут влиять и на итоговый запрос к СУБД, и на его производительность - это отдельно разобрано в [стандарте по эффективным условиям запросов](https://its.1c.ru/db/content/v8std/src/300/200/i8100658.htm).

### 4. Официальные стандарты и проверки

Если вопрос связан с качеством или совместимостью, проверяем:

- документацию 1С;
- стандарты разработки;
- официальные проверки;
- актуальные ограничения платформы/EDT.

Для обычной навигации по стандартам удобно использовать [zeegin/v8std](https://github.com/zeegin/v8std): он собирает стандарты в более обозримом виде и связывает их с диагностическими инструментами. Это удобный индекс, а не замена первичному источнику: значимые нормативные утверждения сверяются с [системой стандартов 1С на ИТС](https://its.1c.ru/db/v8std).

### 5. Проверенный внешний пример

Если остался конкретный пробел, можно открыть:

- другую типовую конфигурацию;
- открытый проект;
- заранее выбранный пример;
- завершённое исследование.

Внешний проект - это источник идей и доказательств, а не команда копировать его целиком.

### 6. Своя реализация

Только после этого пишем недостающую часть самостоятельно.

## Не надо исследовать всё подряд

Принцип "сначала источники" не означает:

> перед каждой строкой кода прочитать БСП, ERP, УТ, БП и десяток GitHub-репозиториев.

Нужно найти **минимальный источник**, который отвечает на важный вопрос.

Ответ найден - исследование заканчивается.

## Пример

Нужно запускать длительный расчёт из управляемой формы, показывать прогресс и не блокировать клиент.

Плохой путь:

1. сразу написать собственный фоновый запуск;
2. придумать своё хранение состояния и опрос прогресса;
3. потом обнаружить, что в проекте или БСП уже используется подходящий механизм длительных операций.

Хороший путь:

1. проверить текущую конфигурацию и существующие похожие сценарии;
2. проверить публичный интерфейс БСП для фактической версии;
3. переиспользовать принятый механизм и добавить только недостающую связку;
4. проверить реальный сценарий в клиенте.

## Если источники противоречат друг другу

Приоритет обычно такой:

1. фактический текущий проект;
2. актуальная стандартная реализация;
3. официальный стандарт;
4. заранее проверенный пример;
5. общий пример из сообщества.

Если важный факт не удалось подтвердить, он остаётся **неизвестным**.

В техническом отчёте это может быть записано как `SOURCE_GAP` или `UNKNOWN`.

Это лучше, чем придумать уверенный ответ без основания.

## Не исследовать очевидное

Source First не означает "всегда сначала исследование".

Если текущий проект уже показывает правильный механизм и существенных неизвестных нет - используйте короткий путь.

Если неизвестен один важный факт - проверяется только он. Глубокое исследование нужно только для действительно широкого или высокорискового вопроса.
