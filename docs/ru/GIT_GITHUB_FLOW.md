# Git и GitHub: как ведётся задача

Этот файл - объяснение **для человека**, в первую очередь для 1С-разработчика, который ещё не привык к Git/GitHub.

Технические инструкции для агента находятся в `AGENT_START.txt` и `.1c-ai/core/GIT_GITHUB_FLOW.md`.

## Зачем это вообще нужно

Главная идея: существенное изменение не должно появляться "непонятно откуда".

По каждой задаче должно быть видно:

- зачем её начали;
- кто и что менял;
- какой код был до и после;
- что проверили;
- на каком этапе нашли ошибку;
- почему изменение в итоге попало в стабильную версию.

Git хранит историю исходного кода. GitHub хранит задачи, обсуждения, Pull Request и результаты автоматических проверок.

## Минимальный словарь

### Git

Система контроля версий. Она хранит историю изменения файлов и позволяет вернуться к предыдущему состоянию.

### GitHub

Сервис вокруг Git: репозиторий, задачи, Pull Request, проверки, история изменений и совместная работа.

<a id="issue"></a>
### Issue - карточка задачи, ошибки или предложения

Issue (часто говорят "ишью") - это обычная карточка в GitHub. В зависимости от ситуации это может быть задача на разработку, ошибка, вопрос, исследование или предложение по улучшению.

Для 1С-разработчика проще всего воспринимать Issue как привычную задачу в трекере, только она живёт рядом с исходниками и историей изменений.

Например:

```text
Issue #42
Перевести формирование тяжёлого отчёта на существующий механизм длительных операций.

Нужно:
- не менять алгоритм расчёта данных;
- сохранить выполнение с правами текущего пользователя;
- проверить запуск, завершение и получение результата в клиенте.
```

В Issue удобно оставить:
- зачем задача появилась;
- какой результат нужен;
- существенные решения и уточнения;
- ссылки на ветку/PR/проверки;
- короткий итог после завершения.

Поэтому новый чат или новый разработчик может продолжить работу по Issue, не восстанавливая всю историю из переписки.

**Issue не является обязательным именно потому, что это GitHub.** Если проект уже использует Jira, YouTrack, Redmine, корпоративный трекер или другой надёжный долговременный носитель задач, методика может использовать его. Важно, чтобы задача имела устойчивый идентификатор и не жила только в чате.

### Commit - зафиксированное изменение

Снимок изменений в Git.

У каждого commit есть уникальный идентификатор - **SHA**. Например:

`891adbb102a315...`

По SHA можно точно понять, какую именно версию кода проверяли.

### Branch - ветка

Отдельная линия разработки.

Она позволяет делать задачу, не ломая стабильный код.

### Pull Request, или PR

Запрос на слияние одной ветки в другую.

PR показывает изменения, результаты проверок и позволяет провести ревью перед слиянием.

### CI - автоматические проверки

Набор проверок, которые GitHub запускает автоматически: например, валидатор структуры, тесты или сборку.

## Три уровня веток

В этой методике по умолчанию используются три уровня.

### `main` - стабильная версия

Сюда попадает только то, что уже прошло интеграционную проверку.

Обычная разработка напрямую в `main` не ведётся.

### `preprod` - интеграционная версия

Здесь собираются готовые feature-задачи перед попаданием в `main`.

На `preprod` проверяется уже не только конкретная правка, но и то, что несколько принятых изменений нормально работают вместе.

Это фактически кандидат на следующую стабильную версию.

### `feature/*` - одна конкретная задача

Под одну Issue создаётся одна ограниченная ветка, например:

`feature/29-human-agent-doc-split`

Она создаётся **от актуального `preprod`**, а не от старого состояния проекта.

## Полный путь задачи

```text
GitHub Issue
    ↓
актуальный preprod
    ↓
feature/<задача>
    ↓
разработка
    ↓
точечные проверки именно этой задачи
    ↓
PR: feature → preprod
    ↓
слияние в preprod
    ↓
интеграционные проверки на preprod
    ↓
PR: preprod → main
    ↓
main
    ↓
закрытие Issue
```

## Что проверяется в feature-ветке

Feature-ветка должна доказать, что **сама задача** сделана правильно.

В зависимости от задачи это могут быть:

- проверка синтаксиса;
- проверка модели/метаданных;
- точечные автоматические тесты;
- сборка;
- запуск изменённого сценария;
- проверка формы, отчёта или интерфейса;
- ревью изменений.

Не нужно автоматически запускать всё существующее тестирование проекта, если задача затрагивает узкий участок и зависимости известны.

## Что проверяется в preprod

После слияния feature-задачи в `preprod` проверяется уже интеграция.

Здесь обычно уместны:

- полный обязательный CI репозитория;
- тесты затронутых подсистем;
- сборка общей версии;
- проверка совместимости нескольких изменений;
- необходимые проверки в тестовой базе/среде;
- критичные пользовательские сценарии.

Набор проверок зависит от проекта. Важно, что `preprod` должен быть в состоянии, которое не стыдно предложить для `main`.

## Как именно сливаются ветки

### feature → preprod

Для одной законченной задачи допустим **squash merge**: несколько технических commit задачи собираются в один аккуратный commit в `preprod`.

При этом Issue/PR всё равно сохраняют историю того, какой feature SHA проверялся перед слиянием.

### preprod → main

Здесь squash уже не подходит.

`preprod` - это проверенный кандидат на стабильную версию, поэтому его история должна войти в `main` как предок.

Используется обычный merge с сохранением истории.

После успешного merge:

1. GitHub запускает проверки уже на новом `main`;
2. если они зелёные, `preprod` безопасно передвигается вперёд к принятому SHA `main`;
3. следующая feature-ветка снова создаётся от синхронизированного `preprod`.

Так `main` и `preprod` не расходятся по истории, а следующий Pull Request не показывает повторно уже принятые изменения.

Не нужно исправлять такую историю через force-push или принудительный reset веток.

## Когда можно сливать preprod в main

Только когда обязательные проверки зелёные или явно отмечены как неприменимые.

Если важная проверка не выполнена и её результат неизвестен, это не "наверное работает", а **не подтверждено**.

## Почему нельзя обычно править рабочую базу "на лету"

Потому что такая правка:

- может не попасть в Git;
- плохо воспроизводится;
- легко теряется при следующем обновлении;
- не имеет нормальной истории;
- сложнее откатывается;
- может не пройти тесты и ревью.

Экстренная ручная правка возможна только как отдельный явно разрешённый аварийный процесс. Это исключение, а не нормальная разработка.

## Как откатить неудачное изменение

Git хранит историю commit.

Если изменение оказалось плохим, можно:

- исправить его новым commit;
- отменить конкретный commit;
- вернуться к известному рабочему SHA;
- сравнить текущую версию с предыдущей.

Как именно делать откат, зависит от ситуации. Главное - история уже сохранена и изменение не существует только "в голове" или в одной рабочей базе.

## Что должен видеть человек в GitHub

Для нормальной задачи достаточно пройти по цепочке:

`Issue → feature branch → PR в preprod → проверки → PR preprod в main → закрытая Issue`.

По этой цепочке должно быть понятно, что сделали и почему этому изменению доверяют.

## Git/GitHub - рекомендуемый путь, а не единственно возможный

Эта схема остаётся основным рекомендуемым вариантом: она лучше всего даёт точную версию исходников, историю изменений, ревью и проверяемые ссылки.

Методика при этом не обязана работать только с GitHub. Проект без Git должен иметь другое долговременное состояние с точной идентификацией версий/задач и честно признавать более слабые гарантии истории и происхождения результата. Обычная синхронизируемая папка не становится эквивалентом Git.
