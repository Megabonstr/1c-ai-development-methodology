# Как взаимодействуют главный координатор и локальный исполнитель

Этот документ - для человека.

Точный машинный контракт: [`.1c-ai/core/ORCHESTRATION.md`](../../.1c-ai/core/ORCHESTRATION.md).

## Коротко

**Главный координатор** - человеческое название роли `Coordinator Main`.

В обычной задаче есть три роли:

1. **человек** - определяет, что нужно получить, и принимает финальный продуктовый результат;
2. **главный координатор** - держит границы задачи, важные решения и карту знаний;
3. **локальный исполнитель** - работает с исходниками, инструментами и проверками.

Дополнительные агенты подключаются только под узкую работу: поиск, независимую критику, тесты, документацию и т. п.

## Где может работать главный координатор

Где угодно:

- в облачном чате;
- локально;
- в desktop/CLI-агенте;
- у другого поставщика ИИ.

Место запуска не определяет его полномочия.

Текущая схема, на которой эта методика проверяется нами:

```text
облачный ChatGPT
      ↕
    GitHub
      ↕
локальный Codex
```

Это **пример текущей практической реализации**, а не обязательный стек.

Главное правило: существенные решения должны сохраняться в долговременном состоянии проекта. Если координатор сам не может записать решение, это может сделать человек или другой разрешённый инструмент.

## Что делает главный координатор

Обычно он:

- помогает человеку сформулировать задачу;
- фиксирует её границы;
- знает, где лежат нужные документы и исследования;
- определяет, что нельзя менять;
- задаёт критерии готовности;
- передаёт техническую работу исполнителю;
- подключается обратно только при существенной развилке;
- проверяет итоговые изменения и результаты проверок;
- координирует приёмку;
- после принятия связывает итог с точной принятой версией и координирует завершение задачи/короткий итог.

Он не должен управлять каждой строкой реализации.

## Что передаётся локальному исполнителю

Координатор передаёт **готовую исполняемую задачу**, а не процесс, который к ней привёл.

Обычно достаточно:
- ссылки/идентификатора зафиксированной задачи;
- точной версии исходников;
- результата, который надо получить;
- границ и того, что нельзя менять;
- уже принятого механизма либо допустимой границы технического поиска;
- точных ссылок на нужные исходники/решения;
- требуемых проверок;
- условий, при которых надо остановиться и вернуться к координатору;
- способа передать итог.

Исполнитель по умолчанию **не перечитывает** сырой разговор с человеком, историю обсуждений координатора, README/философию, весь backlog, несвязанные исследования, все навыки и все профили. Если дополнительный контекст нужен для конкретного технического вопроса - открывается только он.

## Что делает локальный исполнитель

Получив понятную задачу, исполнитель сам:

- открывает реальный проект;
- проверяет метаданные, типы и API;
- меняет код;
- исправляет обычные ошибки компиляции;
- запускает нужные тесты;
- отлаживает;
- проверяет реальный сценарий;
- возвращает точную версию результата и результаты проверок.

### Не возвращаться по каждой технической ошибке

Плохо:

```text
координатор → исполнитель → ошибка компиляции → координатор
координатор → исполнитель → не тот тип → координатор
координатор → исполнитель → тест упал → координатор
```

Нормально:

```text
координатор
  ↓
исполнитель
  ├─ сделал
  ├─ получил ошибку
  ├─ сам исправил
  ├─ проверил
  └─ довёл до итогового результата
  ↓
координатор
```

## Где проходит граница решения

Координатор отвечает за **что должно получиться, что нельзя менять и что считается принятым результатом**.

Локальный исполнитель отвечает за **как технически получить этот результат в реальном проекте**. Он может уточнять API, типы, пути, сигнатуры и другие дешёвые технические факты самостоятельно.

Если выясняется, что надо изменить бизнес-поведение, архитектурную границу, права/RLS/данные, согласованный объём или смысл приёмки - это уже не техническая деталь, и решение возвращается координатору.

## Когда нужно вернуться к координатору

Только если меняется смысл работы:

- непонятно ожидаемое бизнес-поведение;
- реальная архитектура противоречит задаче;
- нужно сильно выйти за согласованные границы;
- требуется опасное действие без разрешения;
- не хватает обязательных данных;
- нужно изменить критерии готовности;
- задача пересекается с другой областью ответственности.

Обычная техническая ошибка - не такая развилка.

## Можно ли использовать одного агента

Да.

Для маленькой задачи один агент может:

1. сначала зафиксировать задачу как координатор;
2. затем выполнить её как локальный исполнитель;
3. вернуться к роли координатора только если смысл задачи пришлось менять.

Для сложной или рискованной задачи лучше разделять контексты, особенно когда требуется независимая критика или приёмка.

Но есть обязательная граница: если тот же физический агент сам внёс **существенное** изменение, он не может единолично принять и продвинуть это изменение как финально принятое. Финальную приёмку должен дать человек-владелец либо отдельно авторизованный независимый контекст, который это изменение не писал.

При этом обычная самопроверка агента остаётся полезной и не требует отдельного проверяющего для каждой мелкой задачи.

## Кто проверяет результат

В технических правилах встречаются режимы:

- `Writer` - пишет;
- `Reviewer` - перечитывает;
- `Critic` - ищет слабые места;
- `Integrator` - собирает итог.

По умолчанию это режимы работы одного локального исполнителя.

Отдельный независимый проверяющий нужен там, где это явно требуется задачей или риском.

## Как завершается задача

Локальный исполнитель заканчивает работу **локальным результатом и доказательствами**, а не финальным продуктовым отчётом.

После этого главный координатор:

1. проверяет, что нужные доказательства действительно есть;
2. получает требуемую приёмку;
3. связывает итог с точной принятой/доставленной версией;
4. сохраняет **один** короткий долговременный итог;
5. сообщает человеку результат кратко и по-русски;
6. закрывает задачу, если на это есть полномочия.

По умолчанию человеческий итог выглядит так:

```text
Что сделано:
Где изменено:
Как проверено:
Что осталось неизвестным / ограничения:
Принятая версия / результат:
```

Это не новая система отчётности. Итог только ссылается на уже существующие задачу, версию и доказательства. Логи, diff, CI, тесты и история PR остаются там, где они уже хранятся.

Если доказательства чего-то не подтверждают, это остаётся неизвестным. Полный отчёт нужен только когда он явно требуется задачей, риском или передачей клиенту/поддержке.

Один и тот же физический агент может после локального исполнения снова работать как координатор, но для существенного изменения он не может сам себе заменить требуемую независимую/человеческую приёмку.

## Как передаётся состояние

Рекомендуемый вариант - Git/GitHub: задача, комментарии, commit SHA, Pull Request и CI дают понятную историю.

Но обязательный принцип шире:

> работа должна продолжаться по сохранённой задаче и решениям, а не по памяти чата.

Если используется другой надёжный способ хранения состояния, схема ролей не меняется.

## Необязательная автоматизация

Для облачного координатора можно добавить уведомления или мост, который сообщает о существенных развилках.

Это только удобство. Решение должно сначала попасть в долговременное состояние проекта.

Технический шаблон: [Optional Cloud Bridge](../patterns/OPTIONAL_CLOUD_BRIDGE.md).

## Почему так проще

Такой подход:

- не привязывает методику к одной модели ИИ;
- не требует держать весь проект в одном контексте;
- уменьшает бессмысленные возвраты между агентами;
- позволяет менять исполнителя без пересказа всей истории;
- оставляет человеку понятную точку контроля.

## Технические названия

В машинных файлах используются следующие термины:

- главный координатор - `Coordinator Main`;
- область ответственности - `CoordinationScope`;
- ответственный координатор - `OwningCoordinator`;
- локальный исполнитель - `Local Main`;
- зафиксированная задача - `Task Contract`.

Эти названия нужны для точности машинных инструкций, а не для повседневного чтения.

## Сырой запрос и общение с человеком

Координатор приводит к задаче только действительно сырой или неоднозначный запрос. Уже готовая ограниченная задача идёт напрямую в запуск.

Исполнитель не должен заново разбирать всю историю разговора. Ему передаются компактная задача и точные ссылки.

Во время обычной технической работы дорогой исполнитель не описывает каждый шаг. Промежуточное сообщение нужно только при существенном блокере/решении. Человеку результат по умолчанию объясняется коротко и по-русски; технические пакеты между агентами остаются компактными и англоязычными.
