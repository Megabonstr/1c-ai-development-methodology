# Как понять, что задача действительно сделана

Этот документ - для человека.

Точный машинный контракт: [`.1c-ai/core/EVIDENCE_MODEL.md`](../../.1c-ai/core/EVIDENCE_MODEL.md).

## Главная мысль

"Код написан", "ошибок нет" и даже "тесты зелёные" - это **разные утверждения**.

У каждой задачи свой вопрос, который нужно доказать. Например:

- мы точно нашли правильный объект и механизм?
- код хотя бы корректен по структуре и синтаксису?
- автоматический сценарий проходит?
- артефакт собирается?
- изменение реально попало в тестовую базу?
- нужный путь выполнился в 1С?
- пользователь действительно видит правильное поведение в клиенте?
- владелец задачи принял результат?

Методика разделяет эти подтверждения, чтобы одно не подменяло другое.

Короткие коды `SOURCE / STATIC / TEST / BUILD / DEPLOY / RUNTIME / NATIVE / USER_ACCEPTANCE` - внутренние метки этой методики, а не официальная классификация 1С.

## Сначала убедились, что меняем правильное место - SOURCE

**Человеческий вопрос:** мы вообще нашли правильный источник, объект, механизм и контракт?

Примеры в 1С:

- нашли реальный реквизит формы и его путь к данным, а не угадали по заголовку поля;
- проверили текущую реализацию механизма в проекте;
- нашли подходящий публичный метод БСП;
- подтвердили формат обмена по текущему проекту или авторитетной документации.

Это подтверждает, что решение опирается на реальный источник.

Но это **не доказывает**, что новый код компилируется, запускается или даёт правильный результат пользователю.

В машинном отчёте это обозначается как `SOURCE`.

## Проверили код и структуру без запуска - STATIC

**Человеческий вопрос:** проходит ли изменение нужные проверки без выполнения бизнес-сценария?

Примеры:

- BSL проходит синтаксическую/статическую проверку;
- запрос разбирается;
- XML имеет ожидаемую структуру;
- модель EDT не показывает нужной ошибки;
- права, формы или метаданные прошли выбранную статическую диагностику.

Для ориентира:

- официальный [v8-code-style](https://github.com/1C-Company/v8-code-style/blob/master/docs/checks/check_index.md) содержит статические проверки BSL, метаданных, форм, запросов и прав;
- официальный [dt-project-checks](https://github.com/1C-Company/dt-project-checks) проверяет структурную целостность EDT-проекта;
- [BSL Language Server](https://1c-syntax.github.io/bsl-language-server/diagnostics/) даёт дополнительный настраиваемый набор статических диагностик.

**Критическая граница:** корректный BSL-синтаксис не означает, что управляемая форма реально работает.

В машинном отчёте это `STATIC`.

## Прогнали автоматический сценарий - TEST

**Человеческий вопрос:** прошёл ли конкретный автоматизированный сценарий с ожидаемым результатом?

Например:

- тест проверил заполнение реквизита;
- тест отчёта сравнил нужное значение;
- интеграционный тест подтвердил конкретный ответ/обработку;
- YAxUnit выполнил сценарий и его утверждения прошли.

В документации YAxUnit тест задаёт ожидаемый результат и сравнивает его с фактическим: [первый тест](https://bia-technologies.github.io/yaxunit/docs/getting-started/first-test/), [запуск тестов](https://bia-technologies.github.io/yaxunit/docs/getting-started/run/).

Зелёный тест доказывает **только тот сценарий и те проверки, которые действительно были выполнены**.

Он не доказывает автоматически поведение всех форм, все права, все варианты данных и весь продукт.

В машинном отчёте это `TEST`.

## Получили собираемый результат - BUILD

**Человеческий вопрос:** можно ли из этих исходников получить нужный артефакт?

Примеры:

- конфигурация/расширение успешно собрано;
- внешняя обработка или отчёт сформированы;
- проект дал ожидаемый build-артефакт.

Это доказывает, что сборка успешна.

Но **сборка не доказывает запуск**.

В машинном отчёте это `BUILD`.

## Изменение реально применили к среде - DEPLOY

**Человеческий вопрос:** попало ли изменение туда, где его нужно проверять?

Примеры:

- конфигурация загружена в тестовую базу;
- расширение установлено;
- обновление структуры БД прошло успешно;
- артефакт применён к нужной тестовой среде.

Это доказывает факт применения.

Но, например, **успешная проверка метаданных EDT не доказывает успешное обновление базы**, а успешное обновление базы не доказывает правильную бизнес-логику.

В машинном отчёте это `DEPLOY`.

## Код действительно выполнился в 1С - RUNTIME

**Человеческий вопрос:** нужный путь реально выполнялся в работающей 1С?

Примеры:

- изменённая обработка запущена в тестовой базе;
- код дошёл до нужной ветки;
- запрос выполнился на фактических тестовых данных;
- обмен реально обработал пакет;
- сценарий выполнен в runtime, а не только проверен статически.

Это подтверждает конкретное выполнение.

Но runtime-вызов сам по себе ещё не доказывает, что пользователь увидел правильную форму, команду или поведение интерфейса.

В машинном отчёте это `RUNTIME`.

## Проверили то, что реально видит пользователь - NATIVE

**Человеческий вопрос:** наблюдали ли мы нужное поведение в настоящем клиенте/EDT/UI?

Примеры:

- форма реально открылась;
- команда видна и доступна;
- динамический список показывает ожидаемый результат;
- событие формы отработало в клиенте;
- пользовательский переход/диалог ведёт себя как требуется;
- отчёт отображается так, как должен выглядеть для пользователя.

Это важно там, где статическая проверка или runtime-вызов не доказывают интерфейс.

**Но и здесь есть граница:** screenshot или открытая форма могут подтвердить конкретное наблюдаемое состояние, но не все бизнес-сценарии этой формы.

В машинном отчёте это `NATIVE`.

## Человек подтвердил, что результат подходит - USER_ACCEPTANCE

**Человеческий вопрос:** владелец задачи принял требуемое бизнес-/пользовательское поведение?

Это нужно не для каждой мелкой технической задачи, но важно, когда смысл результата должен подтвердить пользователь, заказчик или владелец продукта.

Приёмка не заменяет обязательные технические проверки. Она отвечает на другой вопрос: **тот ли результат мы получили с точки зрения задачи**.

В машинном отчёте это `USER_ACCEPTANCE`.

## Главное правило: один вид проверки не заменяет другой

Типичные ошибки:

- BSL без синтаксических ошибок → "форма работает";
- EDT metadata validation → "база успешно обновится";
- build успешен → "код реально выполнился";
- runtime-вызов прошёл → "пользовательский интерфейс ведёт себя правильно";
- форма открылась на screenshot → "проверены все варианты бизнес-процесса";
- тест прошёл на старом commit → "значит проверена текущая версия".

Так делать нельзя.

Каждая проверка отвечает только на свой вопрос.

## Доказательство должно относиться к точной версии результата

Полезно знать не только **что** проверили, но и **что именно** было проверено.

Сильнее выглядит доказательство, которое связано с точным результатом:

- commit SHA;
- hash/идентификатор артефакта;
- test run/job ID;
- конкретная среда и версия платформы;
- точное действие приёмки.

Например, "тесты проходили вчера" слабее, чем "этот test run относится к commit X".

Историческая проверка не становится доказательством новой версии автоматически.

## PASS, FAIL, NOT_REQUIRED и UNKNOWN

Для нужного вида проверки состояние должно быть честным.

### PASS

Проверка выполнена и нужный результат подтверждён.

### FAIL

Проверка выполнена и выявила проблему.

### NOT_REQUIRED

Эта проверка **действительно не нужна** для утверждения, которое мы хотим доказать.

Пример: изменение только документации не требует запуска 1С.

### UNKNOWN

Проверка имела бы значение для утверждения, но её не выполнили, она недоступна или результат нельзя честно подтвердить.

Например: форма должна быть проверена в реальном клиенте, но тестовой базы сейчас нет. Это не `NOT_REQUIRED`, а `UNKNOWN`.

## Пример: небольшая правка внешней обработки

Допустим, изменили внешнюю обработку и её форму.

Можно получить такой набор:

```text
SOURCE = PASS
нашли правильный механизм и точный изменяемый объект

STATIC = PASS
код/структура прошли требуемые проверки

TEST = PASS
целевой автоматический сценарий прошёл

BUILD = PASS
EPF успешно собрана

DEPLOY = NOT_REQUIRED
отдельная установка для этой проверки не нужна

RUNTIME = PASS
EPF запущена в тестовой базе, нужный путь выполнен

NATIVE = PASS
форма реально открыта и проверена в клиенте

USER_ACCEPTANCE = UNKNOWN
владелец задачи ещё не выполнял приёмку, хотя она требуется
```

Такой результат гораздо информативнее фразы "всё зелёное".

## Кто этим пользуется

В первую очередь эта модель нужна агенту/разработчику и координатору, чтобы не смешивать разные виды подтверждений.

Человеку не обязательно запоминать коды.

Практический вопрос проще:

> Какие утверждения о результате вы сейчас делаете - и какая проверка действительно доказывает каждое из них?

Глубина и набор нужных проверок зависят от задачи. Об этом - [Как выбрать достаточный способ проверки задачи](VERIFICATION_PROFILES.md).

## Итоговое описание не является доказательством

Агент может кратко объяснить:

- что изменил;
- где;
- почему выбран этот механизм;
- как проверил;
- что осталось неизвестным.

Это полезная навигация по результату, но она не заменяет исходники, diff, test/build/runtime/native evidence и требуемую приёмку.
