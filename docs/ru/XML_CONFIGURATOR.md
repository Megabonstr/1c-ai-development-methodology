# XML-исходники + Конфигуратор - что это и когда использовать

Этот документ - для человека.

Точный технический профиль: [`.1c-ai/profiles/1c-xml-configurator/PROFILE.md`](../../.1c-ai/profiles/1c-xml-configurator/PROFILE.md).

## Что такое XML-путь

Конфигурацию 1С, расширение, внешнюю обработку или отчёт можно хранить как выгруженные **XML-исходники**.

В таком проекте на диске находятся:

- описания объектов метаданных;
- формы;
- роли;
- СКД;
- модули;
- расширения;
- внешние обработки/отчёты;
- служебные XML-файлы.

Сборка и загрузка выполняются через Конфигуратор или командную строку 1С.

Git часто используется для истории этих файлов, но XML-путь определяется не Git, а тем, **какое представление исходников является главным для проекта**.

## Это полноценный путь, а не запасной вариант EDT

XML + Конфигуратор подходит, если:

- EDT не используется;
- проект уже хранит XML-исходники;
- команда работает через Конфигуратор/CLI;
- сборка автоматизирована вокруг `1cv8 /DESIGNER`;
- агенту удобно работать с файловым деревом.

## Как выглядит техническая работа

Например, нужно изменить форму внешней обработки.

```text
получить зафиксированную задачу
→ локальный исполнитель открывает текущий XML формы
→ сверяет точную структуру по подходящему источнику/навыку
→ вносит изменение
→ проверяет XML
→ собирает EPF
→ запускает в тестовой базе
→ при необходимости открывает настоящую форму
→ возвращает точную версию результата и результаты проверок
```

Как задача хранится, ветвится и принимается - отдельный слой.

Рекомендуемый Git/GitHub-вариант: [Git и GitHub: как ведётся задача](GIT_GITHUB_FLOW.md).

## Главное правило: не угадывать XML

XML 1С сложный.

Там важны:

- пространства имён;
- UUID;
- порядок элементов;
- ссылки между файлами;
- структура конкретного типа объекта.

Поэтому агент не должен писать XML только по памяти модели.

Порядок:

1. текущий проект;
2. точная спецификация или проверенный источник;
3. изменение;
4. проверка.

## Почему валидного XML недостаточно

Это разные факты:

```text
XML корректен
≠
Конфигуратор его принимает
≠
результат собирается
≠
изменение загружается
≠
сценарий реально работает
≠
форма ведёт себя правильно
```

Подробнее о слоях проверки: [Как понимать проверки результата](EVIDENCE_MODEL.md).

## Работа с информационной базой

Загрузка конфигурации и обновление базы могут менять целевую ИБ.

Такие действия должны быть явно разрешены задачей и выполняться в подходящей тестовой/целевой среде.

## Когда выбрать EDT вместо XML

Если настоящие исходники проекта ведутся в EDT и команда работает через EDT, выбирайте EDT-путь.

Выбор зависит от реального владельца исходников, а не от того, какой инструмент случайно доступен агенту.
