# Архитектура простыми словами

Этот документ - для человека. Точные машинные правила находятся в [технической модели репозитория](../architecture/REPOSITORY_MODEL.md) и в `.1c-ai/core/`.

## Главная идея

Методика разделяет **кто принимает решения**, **кто выполняет работу** и **где хранится состояние задачи**.

```text
человек
  ↓
главный координатор
  ↓
зафиксированная задача и решения
  ↓
локальный исполнитель
  ↓
изменение + проверки
  ↓
приёмка
```

- Человек определяет продуктовый смысл и принимает финальные пользовательские решения.
- Главный координатор держит границы задачи, ключевые решения и карту знаний.
- Локальный исполнитель работает с реальными исходниками и доводит техническую часть до проверяемого результата.
- Важное состояние хранится так, чтобы работа переживала новый чат или смену агента.

## Это не один обязательный набор программ

Три решения выбираются независимо.

### 1. Где работает главный координатор

Он может работать:

- в облачном чате;
- локально;
- в desktop/CLI-агенте;
- в другом изолированном контексте.

Для маленькой задачи один физический агент может последовательно быть и координатором, и исполнителем. Важно не смешивать незаметно постановку задачи и её изменение во время реализации.

Подробнее: [Оркестрация](ORCHESTRATION.md).

### 2. Где хранится состояние задачи

Лучше всего в этой методике отработан **Git + GitHub**:

```text
задача
→ ветка
→ изменение
→ проверки
→ Pull Request
→ принятая версия
```

Это удобно из-за истории, сравнения изменений, точных SHA, проверки изменений и автоматических проверок (CI).

Но GitHub не является самой архитектурой. Можно использовать другой надёжный способ хранения задач и решений, если он сохраняет те же границы и позволяет восстановить состояние без старого чата.

Если проект принципиально работает без Git/GitHub, сейчас есть только [проектирование локального durable-state варианта](../research/GITLESS_LOCAL_STATE_V1.md). Operational backend ещё не поставляется: Gitless считается `DESIGNED_DEGRADED_COMPATIBILITY` и может использоваться только поверх уже работающего проектного носителя состояния; иначе lifecycle остаётся `UNKNOWN/BLOCKED` до [#1](https://github.com/Megabonstr/1c-ai-development-methodology/issues/1).

Подробнее: [Git и GitHub](GIT_GITHUB_FLOW.md).

### 3. Как агент работает с 1С

Способ выполнения выбирается по тому, где находятся настоящие исходники проекта:

- [EDT + MCP](EDT_MCP.md);
- [XML + Конфигуратор](XML_CONFIGURATOR.md).

Это отдельный выбор. Например, локальный координатор может работать и с EDT-проектом, и с XML-проектом.

## Как устроен сам репозиторий

### Для человека

`README.md` и `docs/ru/` объясняют методику обычным языком.

Начать лучше с [быстрого старта](GETTING_STARTED.md).

### Для ИИ-агента

`AGENT_START.txt` - короткая точка входа.

`.1c-ai/core/` - точные общие правила.

`.1c-ai/router/` - выбор нужного процесса и способа выполнения.

`.agents/skills/1c-ai-*/` - универсальные рабочие навыки. Актуальный канонический список: [Навыки](SKILLS.md).

`.1c-ai/profiles/` - правила для конкретного способа работы с 1С.

### Для проектных знаний

Проект хранит свои знания отдельно от пакета методики.

Рекомендуемая краткая карта - `PROJECT_AI.md`.

Подробнее: [Структура проекта](PROJECT_STRUCTURE.md).

### Для источников

`sources/` фиксирует внешние материалы, которые действительно повлияли на методику.

Подробнее: [Источники и заимствования](SOURCES_AND_ADOPTION.md).

## Почему всё не собрано в один файл

Человеку нужен обзор и понятная навигация.

Агенту, наоборот, нужен только небольшой кусок контекста для текущей задачи.

Поэтому методика специально разделена на человеческие объяснения, машинные правила, навыки и профили.

## Технические названия

В машинных файлах используются точные термины:

| По-человечески | Технический термин |
|---|---|
| главный координатор | `Coordinator Main` |
| область ответственности | `CoordinationScope` |
| ответственный координатор | `OwningCoordinator` |
| локальный исполнитель | `Local Main` |
| зафиксированная задача | `Task Contract` |

Запоминать их для первого запуска не нужно.
